## 1 协程是什么

协程是 Kotlin 的**用户态并发框架**：把任务从线程里解耦出来，由编译器和运行库实现可暂停、可恢复的执行单元。一句话：**协程 = 挂起能力 + 调度器 + 结构化并发**，它最终仍跑在线程上，只是"何时挂起、恢复后去哪"由库决定。

* **轻量**：一个协程只是堆上的对象（`Job` + `Continuation` + 状态机），创建是纳秒级；线程栈默认约 1MB。10 万个协程很轻松，10 万个线程会 `OutOfMemoryError`。
* **挂起不阻塞线程**：挂起时保存恢复所需的状态（局部变量 + 续体），线程立刻回去执行别的任务。
* **与线程池的关系**：协程是任务，线程池是执行资源。`Dispatchers.Default/IO` 背后是 `CoroutineScheduler` 线程池；协程可以在 A 线程挂起、在 B 线程恢复。

```kotlin
fun main() = runBlocking {
    val jobs = List(100_000) { launch { delay(1_000L); print(".") } }
    jobs.forEach { it.join() }
}
// 换成 100_000 个 thread { Thread.sleep(1000) } 通常会 OOM：
// java.lang.OutOfMemoryError: unable to create native thread
```

`runBlocking` 会阻塞当前线程，只适合 `main` 和测试；Android 上应该用 `lifecycleScope`/`viewModelScope`。

### 1.1 挂起与恢复
`delay(1000)` 不会让线程睡 1 秒：它把当前续体注册到调度器的延时队列并**让出线程**，到点后由调度线程恢复。所以挂起前后可能不在同一个线程：

```kotlin
launch(Dispatchers.Default) {
    println("before: ${Thread.currentThread().name}")
    delay(100)
    println("after: ${Thread.currentThread().name}")   // 线程名可能变了
}
```

`Thread.sleep` 占住线程且不可取消，`delay` 释放线程且可取消，这是两者最本质的区别。

### 1.2 suspend 的本质：CPS 变换 + 状态机
编译器对 `suspend fun loadUser()`（内部依次调用 `fetchToken()`、`fetchUser()`）做两件事：**CPS 变换**（多一个 `Continuation<T>` 参数，返回值变 `Any?`，挂起时返回 `COROUTINE_SUSPENDED`）和**状态机**（按挂起点切段，`label` 记录执行位置，字段保存跨挂起点存活的局部变量）。

```kotlin
// 编译后大致等价于（伪代码，省略异常处理）：
fun loadUser(id: String, completion: Continuation<User>): Any? {
    val sm = completion as? LoadUserSM ?: LoadUserSM(completion)
    if (sm.label == 0) {
        sm.label = 1
        val r = fetchToken(sm)                     // 把自己当续体传下去
        if (r == COROUTINE_SUSPENDED) return r     // 让出线程
        sm.token = r as Token
    }
    sm.label = 2
    val r2 = fetchUser(id, sm.token!!, sm)
    if (r2 == COROUTINE_SUSPENDED) return r2
    return r2
}
// 恢复时：LoadUserSM.invokeSuspend(result) 先存 result，
// 再调用 loadUser(id, this)，由 label 决定从哪继续。
```

* `suspend` 在 JVM 层就是多一个 `Continuation` 参数；能力来自"返回 `COROUTINE_SUSPENDED` + 恢复时调用 `invokeSuspend`"这套约定。
* 因为需要 `Continuation`，`suspend` 函数只能在协程或另一个 `suspend` 函数里调用；挂起本身**不切线程**，切线程是 `withContext`/`Dispatchers` 的职责。

## 2 结构化并发

### 2.1 CoroutineScope、Job、CoroutineContext
* `CoroutineScope`：作用域，持有 `CoroutineContext`，提供 `launch`/`async`，回答"协程归谁管、何时一起取消"。
* `Job`：协程句柄与生命周期节点（`isActive`/`isCancelled`），支持 `join()`/`cancel()`，多个 Job 组成树。
* `CoroutineContext`：`Job + Dispatcher + CoroutineName + CoroutineExceptionHandler` 的集合，`+` 合并，同 key 右侧覆盖左侧。

### 2.2 父子关系
* **父等子**：父协程等所有子协程结束才完成；`runBlocking`/`coroutineScope` 返回时子协程一定都结束了。
* **取消向下**：父 `cancel()` 递归取消所有子协程。
* **失败向上**：子协程抛非 `CancellationException` → 取消父 → 取消兄弟；`CancellationException` 只取消自己。

价值：协程生命周期被限制在词法作用域内，不用手动收集 Job，也不会"页面销毁了任务还在跑"。

### 2.3 SupervisorJob
`SupervisorJob` 的子协程失败**不会**取消父级和兄弟；但它不吞异常，根协程的异常仍交给 `CoroutineExceptionHandler`，没有 handler 一样崩溃。`viewModelScope`/`lifecycleScope` 内部就是 `SupervisorJob() + Dispatchers.Main.immediate`。

### 2.4 coroutineScope vs supervisorScope

| 对比项 | `coroutineScope` | `supervisorScope` |
| --- | --- | --- |
| 失败传播 | 任一子协程失败 → 取消全部子协程并抛给调用方 | 子协程失败不影响兄弟和自身 |
| 异常去向 | 调用方 `try/catch` 能接住 | `launch` 走处理器，`async` 存进 `Deferred` |
| 适用 | 必须同生共死的并行任务 | 互不影响的独立任务 |

```kotlin
suspend fun loadDashboard(): Dashboard = coroutineScope {
    val user = async { repo.loadUser() }      // 任一失败，整体失败
    val orders = async { repo.loadOrders() }
    Dashboard(user.await(), orders.await())
}
```

### 2.5 GlobalScope 为什么被弃用
`GlobalScope`（`@DelicateCoroutinesApi`）等价于"没有父级的协程"：页面销毁后仍在跑并持有 UI 引用；无法统一取消；异常直接进线程未捕获处理器，外层 `try/catch` 接不住；也无法用 `TestScope` 控制。

```kotlin
// ✅ 业务放 ViewModel，Activity 只负责按生命周期收集
private val viewModel: DetailViewModel by viewModels()
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.detail.collect { textView.text = it.title }
    }
}
viewModel.load(intent.getStringExtra(EXTRA_ID)!!)
```

需要长生命周期时自建 scope 并显式取消：`CoroutineScope(SupervisorJob() + Dispatchers.IO)`，在 `close()` 里 `scope.cancel()`。

## 3 调度器

| 调度器 | 线程来源 | 适用场景 | 注意 |
| --- | --- | --- | --- |
| `Dispatchers.Main` | 主线程（Looper） | 更新 UI | 不能耗时；`Main.immediate` 已在该线程时不 post |
| `Dispatchers.IO` | 共享池，阻塞线程上限默认 64 | 文件、数据库、网络 | 不是"一请求一线程" |
| `Dispatchers.Default` | 共享池，并行度 `max(2, CPU 核数)` | JSON、排序、加解密、图片 | CPU 密集，别放阻塞 IO |
| `Dispatchers.Unconfined` | 不切换线程 | 测试、极轻量逻辑 | 恢复线程不确定，生产慎用 |

### 3.1 withContext 切换线程
```kotlin
suspend fun loadAndParse(): List<Article> = withContext(Dispatchers.IO) {
    val json = api.fetchArticleJson()
    withContext(Dispatchers.Default) { parser.parse(json) }   // 切到 CPU 池
}

viewModelScope.launch {                        // 默认主线程
    _uiState.value = UiState.Success(repo.loadAndParse())    // 挂起后自动切回
}
```

`withContext` 不返回 Job，挂起当前协程并在执行完后返回结果，异常/取消按结构化并发传播。**要结果、要顺序**用它，**要并发、要后台跑**用 `launch`/`async`。

## 4 启动模式

### 4.1 launch vs async

| 对比项 | `launch` | `async` |
| --- | --- | --- |
| 返回值 | `Job` | `Deferred<T>` |
| 用途 | 不关心结果 | 需要结果 |
| 异常 | 立即向父协程传播 | 存入 `Deferred`，`await()` 时抛出 |
| 坑 | 异常没人处理导致崩溃 | 只 `async` 不 `await`，异常静默丢弃 |

准确说法：`launch` 的异常立刻取消父协程（除非父是 `SupervisorJob`）；`async` 的异常先存进 `Deferred`，**只有父是 `SupervisorJob`/`supervisorScope` 时才真正"延迟到 await"**，否则失败仍会立即取消父协程。

```kotlin
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default)
val deferred = scope.async { throw IllegalStateException("先存起来") }
// 不 await 就看不到任何异常；await 时才在这里抛出
try { deferred.await() } catch (e: IllegalStateException) { println(e.message) }
```

### 4.2 CoroutineStart

| 模式 | 行为 |
| --- | --- |
| `DEFAULT` | 立即调度，启动前可取消 |
| `LAZY` | 不启动，直到 `start()`/`join()`/`await()` |
| `ATOMIC` | 立即启动，第一个挂起点前不可取消 |
| `UNDISPATCHED` | 在当前线程执行到第一个挂起点，不经过调度器 |

`launch(start = CoroutineStart.LAZY) { ... }` 需要 `start()` 才执行；`withContext` 内部用 `UNDISPATCHED`，先在当前线程执行，遇到真正的挂起再交给调度器。

## 5 取消与异常

### 5.1 协作式取消
`cancel()` 只把 Job 置为 cancelling，**不会中断线程**。协程必须在挂起点（`delay`、`await`、`emit`、`withContext`…）或主动检查 `isActive`/`ensureActive()` 时才会响应：

```kotlin
val job = scope.launch(Dispatchers.Default) {
    while (isActive) { /* 纯计算循环必须主动检查 */ }
}
job.cancelAndJoin()             // cancel + join，等它真正结束
```

阻塞调用（`Thread.sleep`、`InputStream.read`）不响应取消，要换成可取消的 API（OkHttp 的 `Call.cancel()`、关闭流），或用 `runInterruptible` 包装。

### 5.2 不要吞掉 CancellationException
`CancellationException` 是 `Exception` 的子类，`catch (e: Exception)` 会把它一起抓住；吞掉后协程"取消了却还在跑"，父协程永远等不到它结束。错误写法就是 `catch (e: Exception) { Log.e(...) }`，正确写法必须先重新抛出取消：

```kotlin
viewModelScope.launch {
    try {
        while (true) { delay(1_000); poll() }
    } catch (e: CancellationException) {
        throw e
    } catch (e: IOException) {
        Log.e(TAG, "io error", e)
    }
}
```

`finally` 里如果清理逻辑会挂起，要放在 `withContext(NonCancellable) { ... }` 中，否则会立刻再抛 `CancellationException`。

### 5.3 withTimeout 与异常处理器
```kotlin
val user = withTimeout(3_000) { api.loadUser() }          // 超时抛 TimeoutCancellationException
val maybe = withTimeoutOrNull(3_000) { api.loadUser() }   // 超时返回 null

val handler = CoroutineExceptionHandler { _, e ->
    Log.e(TAG, "未捕获的协程异常", e)
}
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default + handler)
scope.launch { throw IOException("network") }             // 交给 handler
```

* `withTimeout` 只取消它内部的子协程，不取消外层；只对可挂起的代码生效，里面 `Thread.sleep(5_000)` 不会被打断。
* `TimeoutCancellationException` 是 `CancellationException` 子类，不要用 `catch (e: Exception)` 把超时和取消混为一谈。
* `CoroutineExceptionHandler` 只对**根协程**生效，对 `async` 无效；`runBlocking` 里的 `launch` 是子协程，handler 也不生效。

### 5.4 runCatching 的坑
`runCatching` 捕获 `Throwable`，会把 `CancellationException` 当成"失败"：

```kotlin
// ❌ 取消被吞，协程无法正常结束
suspend fun load() = runCatching { api.load() }.getOrElse { emptyList() }

// ✅ 重新抛出取消，只处理业务异常
suspend fun loadSafe() = try {
    api.load()
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    emptyList()
}
```

## 6 Flow

### 6.1 冷流与 flow 构建器
`Flow<T>` 是**冷流**：`flow { }` 只描述"怎么产生数据"，不 collect 就一行都不执行；每次 collect 都重新执行一遍，多个收集者各自独立。

```kotlin
fun ticker(): Flow<Int> = flow {
    var i = 0
    while (true) { emit(i++); delay(1_000) }   // emit 是 suspend
}
// 不 collect 就不执行；ticker().take(3).collect { } 依次输出 0 1 2
```

`emit` 只能在 flow 构建器里调用，并且必须与收集在**同一个协程上下文**：在 `withContext`/`launch` 里 emit 会抛 `IllegalStateException: Flow invariant is violated`，换线程请用 `flowOn`。

### 6.2 中间操作符

| 操作符 | 作用 | 说明 |
| --- | --- | --- |
| `map` / `filter` | 转换 / 过滤 | lambda 是 suspend，可直接调挂起函数 |
| `take` / `drop` | 取前 n 个 / 跳过前 n 个 | `take` 会取消上游 |
| `distinctUntilChanged` | 相邻去重（`equals`） | 搜索框、开关状态常用 |
| `debounce` | 防抖，静默一段时间后才发最后一个 | 搜索输入；`@FlowPreview` |
| `flatMapLatest` | 新值到来时取消上一个内层流 | 搜索、切分类，旧请求作废 |
| `catch` | 捕获**上游**异常 | 不能捕获下游 `collect` 里的异常 |
| `retry` | 重试上游 | `retry(3) { it is IOException }` |
| `flowOn` | 改变上游调度器 | 只影响上游 |

```kotlin
@OptIn(FlowPreview::class, ExperimentalCoroutinesApi::class)
fun search(queryFlow: Flow<String>): Flow<List<Article>> = queryFlow
    .debounce(300).map { it.trim() }.filter { it.isNotEmpty() }
    .distinctUntilChanged()
    .flatMapLatest { repository.search(it) }      // 新查询取消旧请求
    .catch { emit(emptyList()) }
```

`flatMapLatest` 的关键是**取消**：新查询到来时，上一个内层 Flow 的收集协程被取消，Retrofit 的 suspend 请求也随之取消，避免旧结果覆盖新结果。

### 6.3 末端操作符
末端操作符才真正触发收集：`collect`、`collectLatest`、`toList`/`toSet`、`first`/`firstOrNull`、`single`、`last`、`reduce`/`fold`、`launchIn`。

```kotlin
val first = repository.observeArticles().first()      // 只要第一个值，随后取消上游
val titles = repository.observeArticles().map { list -> list.map { it.title } }.toList()
repository.observeArticles().onEach { render(it) }.launchIn(lifecycleScope)
```

## 7 背压与线程

Flow 默认是**顺序**的：生产者和收集者在同一个协程里，收集慢 → `emit` 挂起 → 生产者自然变慢。这是"天然背压"，不丢数据，但上下游无法并行。

| 操作符 | 本质 | 生产/消费 | 丢弃策略 | 适用场景 |
| --- | --- | --- | --- | --- |
| `flowOn(d)` | 改变上游调度器，内部引入 channel | 可并发 | 不丢 | 把 IO 和 UI 分开 |
| `buffer(n)` | 增加 channel 容量（默认 64） | 可并发 | 满了挂起 | 生产快、消费慢 |
| `conflate()` | 等价于 `buffer(CONFLATED)` | 生产不阻塞 | 只保留最新 | UI 只关心最新值 |
| `collectLatest {}` | 新值到来取消上一个收集体 | 收集端"重启" | 未处理完的旧值丢弃 | 搜索、点击、动画 |

```kotlin
flow { repeat(5) { emit(it); delay(100) } }
    .flowOn(Dispatchers.IO)                    // 上游切到 IO，不影响下游
    .buffer(2)
    .collect { delay(300); println(it) }       // 不丢：上下游并发，buffer 满才挂起

searchFlow.collectLatest { query ->            // 新值取消旧处理
    showResult(repository.search(query))
}
```

## 8 StateFlow / SharedFlow / LiveData

### 8.1 三种流的定位
* `Flow`：冷流，每次 collect 重新执行。
* `StateFlow`：热流，**必须有初始值**，永远有当前值（`.value`），只保留最新（conflated），相同值不重复发射（`equals`），`replay = 1`，永不结束。
* `SharedFlow`：热流，可配置 `replay`、`extraBufferCapacity`、`onBufferOverflow`，没有初始值；`MutableSharedFlow()` 默认 `replay = 0`、无缓冲。
* `LiveData`：Android 生命周期感知的数据容器，粘性、主线程、值可空。

### 8.2 对比表

| 对比项 | StateFlow | SharedFlow | LiveData |
| --- | --- | --- | --- |
| 类型 | 热流 | 热流 | 生命周期感知容器 |
| 初始值 | 必须有 | 无 | 可为 `null` |
| 粘性 | 有（`replay = 1`） | 可配 `replay` | 有（新观察者收到旧值） |
| 去重 | 相同值不发射 | 不去重 | `setValue` 相同值也通知 |
| 生命周期感知 | 否 | 否 | 是（自动暂停/恢复） |
| 背压/缓冲 | conflated，只留最新 | 可配 buffer / overflow | 无，总是最新值 |
| 适合 | UI 状态 | 事件、广播 | 老代码、DataBinding、Java |

### 8.3 生命周期感知地收集
```kotlin
// ❌ 页面退到后台仍在 collect，浪费资源（launchWhenStarted 同理：只挂起、不取消上游）
lifecycleScope.launch { viewModel.uiState.collect { render(it) } }

// ✅ STARTED 时启动，STOPPED 时取消，重新可见时重新 collect
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { render(it) }
    }
}
```

Compose 用 `collectAsStateWithLifecycle()`（`lifecycle-runtime-compose`），Fragment 用 `viewLifecycleOwner.lifecycleScope`，否则 `onDestroyView` 之后仍在收集，容易空指针或泄漏。

### 8.4 StateFlow 为什么不能当事件总线
1. **conflated**：快速连发两个事件，收集慢时前一个被覆盖。
2. **必须有值**：事件没有"当前值"语义，只能用 `null`/`Idle` 占位，新订阅者一上来就收到假事件。
3. **粘性 replay**：旋转屏幕、重新 collect 时旧事件会再来一次 → 重复 Toast、重复跳转。
4. **equals 去重**：连续两次相同事件（同样的文案）第二次直接不发射。
5. **无订阅者时事件直接丢**：后台、不可见时发出的事件无法保证送达。

```kotlin
// ViewModel 内：一次性事件用 Channel
private val _events = Channel<UiEvent>(Channel.BUFFERED)
val events = _events.receiveAsFlow()          // 单消费者、无粘性

fun onDeleteClicked(id: Long) {
    viewModelScope.launch { _events.send(UiEvent.Toast("已删除")) }
}
// UI 侧：repeatOnLifecycle(STARTED) 里 collect(viewModel.events)
```

广播型事件可用 `MutableSharedFlow(replay = 0, extraBufferCapacity = 1, onBufferOverflow = BufferOverflow.DROP_OLDEST)`。

## 9 Android 实践

### 9.1 三个 scope 的职责

| scope | 上下文 | 取消时机 | 适合放什么 |
| --- | --- | --- | --- |
| `viewModelScope` | `SupervisorJob() + Dispatchers.Main.immediate` | `ViewModel.onCleared()` | 业务逻辑、网络请求、写库 |
| `lifecycleScope` | `SupervisorJob() + Dispatchers.Main.immediate` | Activity/Fragment `onDestroy()` | 收集 UI 状态、一次性 UI 操作 |
| 自建 `CoroutineScope` | 自己组合 | 自己 `cancel()` | 单例、Manager、Application 级任务 |

### 9.2 ViewModel 只暴露状态
```kotlin
class ArticleViewModel(private val repo: ArticleRepository) : ViewModel() {

    // 列表数据只信数据库这个单一数据源
    val uiState: StateFlow<UiState> = repo.observeArticles()
        .map { UiState.Success(it) }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), UiState.Loading)

    fun refresh() = viewModelScope.launch {
        try {
            repo.refreshArticles()          // 请求网络并写库，Room 的 Flow 会自动重发
        } catch (e: CancellationException) {
            throw e
        } catch (e: IOException) {
            Log.e(TAG, "refresh failed", e)
        }
    }
}
```

`MutableStateFlow` 要私有，对外只给 `StateFlow`（`asStateFlow()`），否则 UI 层能随意改状态，单向数据流就破了。

### 9.3 网络 + 数据库的典型链路
```kotlin
class ArticleRepository(private val api: ArticleApi, private val dao: ArticleDao) {
    // Room 的 @Query 返回 Flow：表一变就重新发射
    fun observeArticles(): Flow<List<Article>> =
        dao.observeAll().map { list -> list.map { it.toArticle() } }

    // Retrofit 的 suspend 函数 + Room 的 suspend 写入
    suspend fun refreshArticles() = withContext(Dispatchers.IO) {
        val remote = api.fetchArticles()
        dao.deleteAll()
        dao.insertAll(remote.map { it.toEntity() })
    }
}
```

链路：用户下拉 → `viewModel.refresh()` → `viewModelScope` 启动 → `withContext(IO)` 里 Retrofit 发请求 → 写 Room → Room 的 `InvalidationTracker` 让 `observeArticles()` 重新发射 → Activity 的 `repeatOnLifecycle` 收到新列表 → 刷新 UI。刷新中的 loading/error 用 `StateFlow`/`Channel` 表达，列表本身只来自数据库，避免"网络结果"和"本地结果"两份状态打架。

## 10 面试高频问答

### 10.1 协程和线程的区别？
* 线程是 OS 调度单位，有内核栈（约 1MB），创建/切换进内核，阻塞就占资源；协程是用户态任务，本质是 `Continuation` 状态机 + `Job` 对象，创建成本极低。
* 协程最终跑在线程上，由 `Dispatchers` 决定线程池；一个线程可顺序跑大量协程，协程也能跨线程恢复。
* 挂起不阻塞线程（线程去干别的），线程 `sleep`/阻塞 IO 会占住线程；线程由 OS 抢占式调度，协程的取消是协作式的。
### 10.2 suspend 函数的原理？
* CPS 变换：多一个 `Continuation` 参数，返回 `Any?`（结果或 `COROUTINE_SUSPENDED`）。
* 状态机：`label` 记录位置，字段保存跨挂起点变量；恢复时 `invokeSuspend(result)` 从 `label` 继续。
* 挂起不切线程，切线程靠 `withContext`/`Dispatchers`；`suspend` 只能在协程或另一个 `suspend` 函数中调用。
### 10.3 结构化并发解决了什么？
* scope 内协程组成 Job 树：父等子、取消向下、失败向上，生命周期被限制在词法作用域内。
* 避免 `GlobalScope` 式泄漏和异常静默丢失，`coroutineScope` 可把子任务失败统一抛给调用方。
* 取消可预测、可测试（`TestScope` 能等所有子协程结束）。
### 10.4 协程的取消是协作式的吗？
* 是。`cancel()` 只置 cancelling，并在挂起点恢复时抛 `CancellationException`，不会杀线程。
* 纯计算/阻塞代码不检查就不停，需要 `isActive`/`ensureActive()`；`finally` 里的挂起清理要用 `NonCancellable`。
* 不要用 `catch (e: Exception)` 吞掉 `CancellationException`，否则协程取消了却还在跑。
### 10.5 launch 和 async 的区别？异常怎么传播？
* `launch` 返回 `Job` 不关心结果；`async` 返回 `Deferred<T>`，`await()` 取结果或异常。
* `launch` 异常立即取消父协程；`async` 异常先存 `Deferred`，但父是普通 Job 时失败仍会立即取消父，只有 `SupervisorJob` 下才是真正"await 才抛"。
* 并行分解用 `async` + `awaitAll()`；只 `async` 不 `await` 会静默丢异常。
### 10.6 SupervisorJob 和 Job 的区别？viewModelScope 为什么用它？
* 普通 `Job` 子失败会取消父和兄弟；`SupervisorJob` 子失败只影响自己。
* ViewModel 中多个请求互不相关，一个失败不该取消其他请求和整个页面。
* `SupervisorJob` 不吞异常：根协程失败仍走 `CoroutineExceptionHandler`，无 handler 一样崩溃。
### 10.7 Flow 和 RxJava 的区别？
* Flow 原生、和协程/结构化并发一体，冷流 + `suspend` 天然背压，学习维护成本低。
* RxJava 操作符更全、线程模型显式（`Schedulers`）、Java 友好；两者可用 `asFlow()`/`asObservable()` 互转。
* 新项目优先 Flow；已有大量 Rx 代码或复杂流组合时保留 RxJava。
### 10.8 StateFlow 和 LiveData 怎么选？
* 新代码/Compose：`StateFlow` 类型安全、可测试、任意线程、能表达 loading/error，配合 `stateIn` 缓存。
* 老代码/DataBinding/Java：`LiveData` 自动生命周期感知、XML 可绑定。
* `StateFlow` 不感知生命周期，UI 必须 `repeatOnLifecycle` 或 `collectAsStateWithLifecycle`；两者可互转。
### 10.9 StateFlow 为什么不能当事件总线？
* conflated：连续事件被覆盖；`replay = 1` 会让旋转屏幕后重放旧事件，重复 Toast/跳转。
* `equals` 去重导致相同事件第二次不发射；而且事件没有"当前值"语义，必须有初始值是硬伤。
* 用 `Channel(BUFFERED).receiveAsFlow()`（单消费者、无粘性）或 `SharedFlow(replay = 0, extraBufferCapacity = N)`。
### 10.10 flowOn、buffer、conflate、collectLatest 的区别？
* `flowOn` 改上游调度器不丢数据；`buffer` 加容量让上下游并发，满了挂起。
* `conflate` 只留最新、生产不阻塞；`collectLatest` 新值取消旧收集体。
* 都通过 channel 传递；换线程用 `flowOn`，不想丢用 `buffer`，只要最新用 `conflate`，旧任务作废用 `collectLatest`。
### 10.11 冷流和热流的区别？shareIn/stateIn 是什么？
* 冷流 collect 才执行，每个订阅者独立跑一遍（`flow {}`、Room 的 `Flow`）。
* 热流数据源独立于订阅者，共享同一份数据（`StateFlow`/`SharedFlow`）。
* `shareIn`/`stateIn` 把冷流转热：共享上游、按 `SharingStarted` 启停；`stateIn` 需初始值，`WhileSubscribed(5_000)` 常用于 ViewModel。
### 10.12 协程泄漏怎么排查？
* 现象：页面销毁后仍有网络回调/Job 未完成，LeakCanary 报 `CoroutineScope`/`Continuation` 持有 Activity/View。
* 常见原因：`GlobalScope`、自建 scope 忘 `cancel()`、长生命周期 scope 捕获 View、`while (true)` 不检查 `isActive`。
* 用 `DebugProbes`/IDE 协程面板 dump Job 树；修复靠 `viewModelScope`/`lifecycleScope` 或显式 `cancelAndJoin()`。
