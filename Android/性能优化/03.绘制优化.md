## 1 简介

绘制优化关注界面流畅度：让每一帧都在 VSYNC 周期内完成，避免掉帧、卡顿和过度绘制。本文从渲染流程讲起，介绍 16ms 的来源、Choreographer 与 VSYNC、过度绘制、布局优化、监控工具和代码实践。

## 2 UI 渲染流程

### 2.1 Measure / Layout / Draw

`ViewRootImpl.performTraversals()` 依次触发 `performMeasure`、`performLayout`、`performDraw`。

* Measure：自顶向下测量，父容器把 `MeasureSpec`（模式 + 尺寸）传给子 View；模式有 `EXACTLY`、`AT_MOST`、`UNSPECIFIED`。
* Layout：自顶向下确定位置，父容器调用子 View 的 `layout()`，由 `onLayout()` 摆放子 View。
* Draw：依次绘制背景、`onDraw`、`dispatchDraw`、前景和滚动条。

测量和布局的代价与树的深度、节点数量成正比。RelativeLayout 会对子 View 测量两次，LinearLayout 使用 `weight` 时也会二次测量；层级越深、`wrap_content` 越多，开销越大。

`requestLayout()` 触发 measure/layout，`invalidate()` 只触发重绘，两者最终都通过 `ViewRootImpl.scheduleTraversals()` 请求下一次 VSYNC。

### 2.2 从 DisplayList 到屏幕

Android 5.0 起，Draw 阶段把绘制命令记录到 **RenderNode / DisplayList**，而不是直接画像素。完整管线：

1. UI 线程处理输入、动画和 traversal，构建 DisplayList。
2. RenderThread 把 DisplayList 转成 GPU 命令。
3. GPU 光栅化，写入 GraphicBuffer。
4. SurfaceFlinger 合成各 Layer，交给 Hardware Composer。
5. 显示控制器按 VSYNC 扫描输出。

UI 线程负责“记录命令”，RenderThread 负责“翻译提交”。主线程耗时会导致帧无法提交，RenderThread 的耗时（shader 编译、纹理上传）同样会掉帧。

## 3 16ms 与掉帧

### 3.1 刷新率、帧率与 VSYNC

屏幕按固定频率刷新，60Hz 每 16.67ms 刷新一次，这就是“16ms 帧预算”。

| 刷新率 | 每帧预算 |
| --- | --- |
| 60Hz | 16.67ms |
| 90Hz | 11.11ms |
| 120Hz | 8.33ms |

VSYNC 是垂直同步信号，表示屏幕即将开始新一轮扫描。应用在 VSYNC 到来时处理下一帧，完成后交给 SurfaceFlinger，等待下一次 VSYNC 显示。

### 3.2 掉帧是怎么发生的

一帧的 UI 线程工作、RenderThread 工作和 GPU 光栅化无法在一个 VSYNC 周期内完成时，SurfaceFlinger 拿不到新帧，只能继续显示上一帧，这就是掉帧（Jank）。

常见原因：

* 主线程做耗时操作：IO、数据库、网络、大量计算、锁等待。
* 布局层级过深，`wrap_content` 或 `weight` 导致重复测量。
* 过度绘制严重，GPU 填充率不足。
* 频繁 GC 或单次 GC 停顿过长。
* 动画过多，或动画刷新频率与屏幕不匹配。
* `onDraw` 中创建对象、图片解码、字体加载落在关键帧上。

平均帧率 60fps 不代表不卡顿，偶发长帧对体感影响更大，线上更应关注帧耗时 P90/P99 和卡顿率。

### 3.3 Choreographer 与 VSYNC

Choreographer 通过 `DisplayEventReceiver` 接收 VSYNC，按优先级执行五类回调：INPUT、ANIMATION、INSETS_ANIMATION、TRAVERSAL（measure/layout/draw）、COMMIT。

`postFrameCallback()` 注册的回调在下一帧的动画阶段执行，常用来统计帧间隔：

```java
Choreographer.getInstance().postFrameCallback(new Choreographer.FrameCallback() {
    private long lastFrameTimeNanos = 0;

    @Override
    public void doFrame(long frameTimeNanos) {
        if (lastFrameTimeNanos != 0) {
            long intervalMs = (frameTimeNanos - lastFrameTimeNanos) / 1_000_000;
            if (intervalMs > 16) {
                // 疑似掉帧，需结合页面可见性和是否有绘制过滤
            }
        }
        lastFrameTimeNanos = frameTimeNanos;
        Choreographer.getInstance().postFrameCallback(this);
    }
});
```

回调运行在 UI 线程，不能做耗时操作。帧间隔变大也可能是因为界面静止没有绘制，需要结合页面可见性和 `FrameInfo` 过滤。

## 4 过度绘制

### 4.1 原理与来源

过度绘制（Overdraw）指同一帧内某个像素被重复绘制。GPU 填充率有限，多余绘制会浪费带宽、增加功耗，严重时掉帧。

常见来源：主题 `windowBackground` 与布局背景重复；列表 item 的多层背景、分割线；半透明遮罩层层叠加；图片尺寸远大于显示尺寸；自定义 View 重复绘制同一区域。

### 4.2 检测

打开开发者选项中的“调试 GPU 过度绘制”，界面按绘制次数着色：

| 颜色 | 含义 |
| --- | --- |
| 蓝色 | 1 次，理想 |
| 绿色 | 2 次，可接受 |
| 粉色 | 3 次，需关注 |
| 红色 | 4 次及以上，需优化 |

该功能只对可调试应用生效。目标是大部分区域为蓝色，避免大面积红色。

### 4.3 优化

* 删除重复背景：`windowBackground` 设为最终背景，去掉布局根节点重复的 `background`。
* 列表 item 只在需要点击反馈时设置 `selectableItemBackground`。
* 用 `canvas.clipRect()` 限定绘制区域，用 `canvas.quickReject()` 跳过不可见区域。
* 减少半透明叠加，能用不透明背景就不用 alpha。
* 图片按显示尺寸解码。
* 对不需要绘制的 ViewGroup 调用 `setWillNotDraw(true)`。
* 用 `merge` 减少层级，但层级少不等于过度绘制少，二者要分别优化。

## 5 布局优化

### 5.1 减少层级

* 优先使用 ConstraintLayout，用约束代替多层嵌套。
* 用 `include` 复用布局，用 `merge` 消除多余根节点。
* 删除只起包裹作用的 FrameLayout/LinearLayout。
* 避免在 RecyclerView item 中使用 `wrap_content`。
* 用 `ViewStub` 延迟加载低频视图。

### 5.2 merge

`merge` 作为根节点时不会生成新 View，子 View 直接添加到父容器：

```xml
<!-- layout_title.xml -->
<merge xmlns:android="http://schemas.android.com/apk/res/android">
    <TextView
        android:layout_width="wrap_content"
        android:layout_height="wrap_content"
        android:text="标题" />
</merge>
```

`merge` 只能作为根节点，且必须配合具体父容器，否则会丢失 `LayoutParams`。

### 5.3 ViewStub

ViewStub 是轻量占位 View，初始不占布局空间，`inflate()` 或设为可见时才加载目标布局：

```xml
<ViewStub
    android:id="@+id/stub_empty"
    android:layout_width="match_parent"
    android:layout_height="wrap_content"
    android:layout="@layout/layout_empty" />
```

```java
ViewStub stub = findViewById(R.id.stub_empty);
stub.setInflatedId(R.id.empty_view);
View emptyView = stub.inflate(); // 只能 inflate 一次
```

适合错误页、空数据页、广告位等低频视图。inflate 后 ViewStub 从父容器移除，替换为目标布局。

### 5.4 ConstraintLayout

* 用约束代替嵌套 LinearLayout。
* 用 `Guideline` 辅助对齐，用 `Barrier` 处理动态宽度。
* 用 `Chain` 实现等分或加权排列，代替 `weight`。
* 用 `layout_constraintDimensionRatio` 保持宽高比。
* 对可能超出约束的文本使用 `layout_constrainedWidth="true"`。

ConstraintLayout 在 `wrap_content` 且相互约束时仍可能多次测量，因此仍需控制复杂度。

## 6 卡顿监控工具

### 6.1 GPU 呈现模式

开发者选项的“GPU 呈现模式分析”以条形图展示每帧各阶段耗时，绿色横线是 16ms 基准，超过说明该帧可能掉帧。

```bash
adb shell dumpsys gfxinfo com.example.app reset
adb shell dumpsys gfxinfo com.example.app
adb shell dumpsys gfxinfo com.example.app framestats
```

`framestats` 输出每一帧各阶段的 CSV 时间戳，对比 DrawStart、SyncStart、IssueDrawCommandsStart 等字段，可以判断耗时发生在 UI 线程还是渲染线程。

### 6.2 Systrace

Systrace 基于 atrace，把 UI 线程、RenderThread、SurfaceFlinger 放在同一时间轴：

```bash
python systrace.py -a com.example.app -t 5 -o trace.html \
    gfx view wm sched freq idle am
```

重点看 Alerts 的掉帧警告、UI Thread 的 `doTraversal`/`measure`/`layout`/`draw`、RenderThread 的 `DrawFrame`、SurfaceFlinger 的合成耗时。Android 10 之后 Systrace 已被 Perfetto 取代。

### 6.3 Perfetto

Perfetto 支持更长采集和 SQL 查询：

```bash
adb shell perfetto -o /data/misc/perfetto-traces/trace.perfetto-trace -t 10s \
    sched freq idle am wm gfx view binder_driver hal dalvik
adb pull /data/misc/perfetto-traces/trace.perfetto-trace
```

把 trace 拖到 `ui.perfetto.dev` 分析，也可以用 textproto 配置采集更精细的数据。线上则通常用 Looper Printer 统计主线程消息耗时，用 Choreographer 统计掉帧率。

## 7 代码示例

### 7.1 onDraw 避免分配对象

`onDraw` 每帧调用，在其中 new 对象会加重 GC：

```java
public class ChartView extends View {
    private final Paint paint = new Paint(Paint.ANTI_ALIAS_FLAG);
    private final Rect clipRect = new Rect();
    private final Path path = new Path();

    public ChartView(Context context) {
        super(context);
        paint.setStyle(Paint.Style.STROKE);
        paint.setStrokeWidth(2f);
    }

    @Override
    protected void onDraw(Canvas canvas) {
        super.onDraw(canvas);
        if (!canvas.getClipBounds(clipRect)) {
            return;
        }
        if (canvas.quickReject(clipRect, Canvas.EdgeType.AA)) {
            return;
        }
        canvas.drawPath(path, paint);
    }
}
```

## 8 总结

* 绘制优化的核心是让每一帧在 VSYNC 周期内完成，60Hz 下为 16.67ms。
* UI 线程构建 DisplayList，RenderThread 提交 GPU 命令，任一环节超时都会掉帧。
* 用 Choreographer、GPU 呈现模式、Systrace/Perfetto 定位问题，线上用 Looper 监控和帧率统计。
* 过度绘制和布局层级是最常见的两个优化点，分别针对 GPU 填充率和 CPU 测量/布局。
* 代码层面避免在 onDraw 中分配对象，减少无效绘制，善用局部刷新。
