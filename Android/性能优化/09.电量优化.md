## 1 电量都去哪了

Android 的耗电本质上来自几个硬件模块，应用能控制的是"让它们工作多久、多频繁"：

| 耗电来源 | 典型场景 | 优化方向 |
| --- | --- | --- |
| CPU | 后台计算、频繁唤醒、死循环 | 减少唤醒次数、批量处理、及时休眠 |
| 网络 | 轮询、频繁小请求、弱网重试 | 合并请求、缓存、推送替代轮询 |
| 传感器 | 加速度计、陀螺仪、光线 | 降低采样率、用批处理、及时注销 |
| 定位 | GPS 高频定位、地理围栏 | 降低精度与频率、复用上次位置 |
| WakeLock | 后台任务长时间持锁 | 带超时、finally 释放 |
| Alarm | 高频定时唤醒 | 用不精确闹钟、合并任务 |

系统的电量统计以"电池毫安时"为单位，但不同机型、不同信号的绝对值差异很大，因此优化时更应关注**相对变化**和**行为次数**（唤醒了多少次、定位了多少次、持锁多久），而不是只看一个百分比。

## 2 Battery Historian 与耗电分析

Battery Historian 是 Google 提供的离线分析工具，可以把 `bugreport` 转成可视化的时间线，查看每个应用的唤醒、网络、定位、Job、WakeLock 等行为。

```bash
# 1. 重置电量统计（可选，便于只看当前场景）
adb shell dumpsys batterystats --reset

# 2. 复现测试场景后抓取报告
adb bugreport bugreport.zip

# 3. 用 Docker 启动 Battery Historian 并上传 zip
docker run -p 9999:9999 gcr.io/android-battery-historian/stable:latest
```

也可以直接看文本统计：

```bash
adb shell dumpsys batterystats --charged com.example.app
adb shell dumpsys batterystats --checkin | grep com.example.app
```

分析时重点看：

* **Mobile radio active / Wi-Fi active**：网络活跃时长，是否有大量短请求。
* **Wake locks**：持锁次数与总时长，尤其关注超过 1 分钟的锁。
* **JobScheduler / Alarm**：任务触发频率是否符合预期。
* **Sensor / GPS / Doze**：传感器与定位启用时间，设备是否进入低电耗模式、应用被分到哪个 Standby 分组。

Battery Historian 只能线下使用，线上还需要埋点统计耗电行为，例如定位次数、WakeLock 持有时长、后台任务执行次数，并随崩溃/性能数据一起上报。

## 3 用 JobScheduler / WorkManager 替代轮询

轮询是后台耗电的头号杀手：每隔几分钟请求一次，不管有没有数据，都会唤醒 CPU 和射频。

### 3.1 JobScheduler

JobScheduler 把任务交给系统统一调度，可以设置网络、充电、空闲等约束，系统会在合适的时机批量执行：

```kotlin
val job = JobInfo.Builder(JOB_ID, ComponentName(context, SyncJobService::class.java))
    .setRequiredNetworkType(JobInfo.NETWORK_TYPE_UNMETERED)
    .setRequiresCharging(true)
    .setPeriodic(15 * 60 * 1000L) // 周期任务最短 15 分钟
    .build()

context.getSystemService(JobScheduler::class.java).schedule(job)
```

### 3.2 WorkManager

WorkManager 在 JobScheduler 之上提供了更好的 API、任务链与保证执行能力，适合绝大多数后台任务：

```kotlin
val constraints = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.UNMETERED)
    .setRequiresCharging(true)
    .build()

val request = PeriodicWorkRequestBuilder<SyncWorker>(15, TimeUnit.MINUTES)
    .setConstraints(constraints)
    .build()

WorkManager.getInstance(context)
    .enqueueUniquePeriodicWork("sync", ExistingPeriodicWorkPolicy.UPDATE, request)
```

* 周期任务最小间隔 15 分钟，系统还会做批量对齐，实际触发时间可能有偏差。
* 一次性任务用 `OneTimeWorkRequest`，需要尽快执行时用 `setExpedited()`。
* 用 `enqueueUniquePeriodicWork` 避免重复入队；任务要幂等，可能因为进程被杀而重试。

### 3.3 什么时候还值得用 Alarm

只有对时间点有严格要求时才用 `AlarmManager`，例如闹钟、日历提醒、用药提醒。普通数据同步、日志上报都应该用 WorkManager。

## 4 Doze 与 App Standby

### 4.1 Doze（低电耗模式）

Android 6.0 引入。设备满足"屏幕关闭、未充电、静止"一段时间后进入 Doze，系统会：

* 延迟网络访问、暂停同步与 Wi-Fi 扫描。
* 延迟 JobScheduler 任务与 Alarm，只在维护窗口（maintenance window）集中放行，窗口间隔逐渐变长。

需要精确触发时可以用：

```kotlin
alarmManager.setExactAndAllowWhileIdle(
    AlarmManager.RTC_WAKEUP,
    triggerAtMillis,
    pendingIntent
)
```

`setExactAndAllowWhileIdle` 在 Doze 下仍会被限频，不能用于高频任务。

### 4.2 App Standby

App Standby 会按用户使用习惯把应用分到不同 bucket（Android 9+）：

| Bucket | 特征 | 任务配额 |
| --- | --- | --- |
| active | 正在使用 | 高 |
| working_set | 近期使用过 | 较高 |
| frequent | 经常使用 | 中 |
| rare | 很少使用 | 低 |
| restricted | 被系统或用户限制 | 极低，几乎只能前台运行 |

应用应尽量在 `active` / `working_set` 时完成关键同步，不要假设后台任务随时能执行。

### 4.3 电池优化白名单

`PowerManager.isIgnoringBatteryOptimizations()` 可以判断应用是否在白名单中。`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 会直接弹窗申请，但 Google Play 对该权限的审核很严格，只有核心功能（如闹钟、通话、健康监测）才允许使用。

## 5 前台服务规范

前台服务适合"用户可感知、需要持续运行"的任务，例如导航、音乐播放、运动记录、文件传输。它不是绕过后台限制的万能钥匙。

```kotlin
class SyncService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        ServiceCompat.startForeground(
            this, NOTIFICATION_ID, buildNotification(),
            ServiceInfo.FOREGROUND_SERVICE_TYPE_DATA_SYNC
        )
        return START_NOT_STICKY
    }

    override fun onBind(intent: Intent?): IBinder? = null
}
```

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_DATA_SYNC" />

<service
    android:name=".SyncService"
    android:exported="false"
    android:foregroundServiceType="dataSync" />
```

规范要点：

* Android 8.0 起后台启动服务会抛异常，必须用 `startForegroundService()` 并在 5 秒内调用 `startForeground()`；Android 10 起必须声明 `foregroundServiceType`。
* Android 12 起从后台启动前台服务受限，可能抛 `ForegroundServiceStartNotAllowedException`；Android 14 起 type 与权限必须匹配，`dataSync` 等类型在 Android 15 上还有每日时长上限。
* 通知要真实反映任务内容，任务结束及时 `stopForeground()` / `stopSelf()`；能用 WorkManager 完成的不要用前台服务。

## 6 定位精度与频率

定位是耗电大户，GPS 尤其明显。优先使用 Google Play Services 的 `FusedLocationProviderClient`，它会在 GPS、Wi-Fi、基站之间自动权衡。

### 6.1 精度选择

| Priority | 精度 | 功耗 | 适用场景 |
| --- | --- | --- | --- |
| `PRIORITY_HIGH_ACCURACY` | 米级 | 很高 | 导航、跑步轨迹 |
| `PRIORITY_BALANCED_POWER_ACCURACY` | 百米级 | 中 | 天气、附近门店 |
| `PRIORITY_LOW_POWER` | 城市级 | 低 | 城市切换、粗略位置 |
| `PRIORITY_PASSIVE` | 复用其他应用结果 | 极低 | 顺便获取位置 |

### 6.2 降低频率与使用批处理

```kotlin
val request = LocationRequest.Builder(Priority.PRIORITY_BALANCED_POWER_ACCURACY, 60_000L)
    .setMinUpdateIntervalMillis(30_000L)
    .setMaxUpdateDelayMillis(120_000L)
    .build()

fusedLocationClient.requestLocationUpdates(request, callback, Looper.getMainLooper())
fusedLocationClient.removeLocationUpdates(callback) // 页面销毁或任务结束时
```

* 只在需要时定位，拿到结果就移除监听；优先用 `getCurrentLocation()` 获取一次位置。
* 复用上一次定位结果并设置过期时间；后台定位需要 `ACCESS_BACKGROUND_LOCATION`（Android 10+），需单独申请且审核严格。
* 地理围栏用 `GeofencingClient`，让系统在进入/离开时通知，不要自己轮询位置。

## 7 WakeLock 使用与释放

WakeLock 让 CPU 或屏幕保持唤醒，滥用会显著增加耗电。

| 类型 | 作用 | 说明 |
| --- | --- | --- |
| `PARTIAL_WAKE_LOCK` | 保持 CPU 运行 | 最常用，屏幕和键盘可以关闭 |
| `ACQUIRE_CAUSES_WAKEUP` | 强制点亮屏幕 | 仅用于闹钟等场景 |
| `ON_AFTER_RELEASE` | 释放后屏幕多亮一会 | 谨慎使用 |

`SCREEN_DIM_WAKE_LOCK`、`SCREEN_BRIGHT_WAKE_LOCK`、`FULL_WAKE_LOCK` 已废弃，不要使用。

```kotlin
val wakeLock = context.getSystemService(PowerManager::class.java)
    .newWakeLock(PowerManager.PARTIAL_WAKE_LOCK, "Sync:upload")
try {
    wakeLock.acquire(10 * 60 * 1000L) // 带超时，避免忘记释放
    // 执行需要保持 CPU 的任务
} finally {
    if (wakeLock.isHeld) wakeLock.release()
}
```

使用要点：

* `acquire()` 与 `release()` 必须配对，释放写在 `finally` 中。
* 优先使用带超时的 `acquire(timeout)`，异常情况下也能自动释放。
* `setReferenceCounted(false)` 可以避免多次 acquire 需要多次 release 的坑；不要用 WakeLock 做定时轮询，用 WorkManager / AlarmManager。检查用 `adb shell dumpsys power | grep -i wake`。

## 8 传感器与 Alarm

### 8.1 传感器

```kotlin
val sensorManager = context.getSystemService(SensorManager::class.java)
val sensor = sensorManager.getDefaultSensor(Sensor.TYPE_ACCELEROMETER)
// 最多延迟 10 秒上报，减少唤醒次数
sensorManager.registerListener(listener, sensor, SensorManager.SENSOR_DELAY_NORMAL, 10_000_000)
sensorManager.unregisterListener(listener) // 页面不可见时
```

* 按需选择采样率（`SENSOR_DELAY_UI` 通常够用），用 `maxReportLatencyUs` 批处理，页面不可见时立即注销。
* 计步优先用 `TYPE_STEP_COUNTER` / `TYPE_STEP_DETECTOR` 硬件传感器，不要自己用加速度计积分。
* 运动检测用 `TYPE_SIGNIFICANT_MOTION`，触发一次即可，不需要持续采样。

### 8.2 Alarm

* 普通定时用 `setInexactRepeating()` 或 WorkManager，让系统合并唤醒。
* 需要精确时间才用 `setExactAndAllowWhileIdle()` / `setAlarmClock()`。
* Android 12 起精确闹钟需要 `SCHEDULE_EXACT_ALARM` 权限，Android 13 起对 `USE_EXACT_ALARM` 有严格限制。
* `PendingIntent` 使用 `FLAG_IMMUTABLE`，requestCode 唯一；任务完成后及时 `cancel()`，换设备/退出登录时清理所有闹钟。

## 9 其他耗电点与监控

* 页面不可见时停止动画、视频、传感器、定位，不要用 `FLAG_KEEP_SCREEN_ON` 长时间保持常亮。
* 减少后台 Wi-Fi/蓝牙扫描；大文件下载、资源更新放到充电 + Wi-Fi 时执行。
* 用 Android Studio 的 Energy Profiler 观察实时曲线；线上接入 Battery-Metrics 统计 Alarm、WakeLock、Camera、CPU、Network 的使用次数与时长。
