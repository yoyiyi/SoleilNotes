## 1 Android 存储与 IO 基础

### 1.1 存储目录

| 目录 | 获取方式 | 特点 |
| --- | --- | --- |
| 内部私有目录 | `getFilesDir()`、`getCacheDir()` | 无需权限，卸载清除，容量有限 |
| 内部数据库 | `getDatabasePath()` | SQLite 数据库默认位置 |
| SharedPreferences | `getSharedPreferences()` | 位于 `shared_prefs` 目录 |
| 外部私有目录 | `getExternalFilesDir()`、`getExternalCacheDir()` | 无需权限，随应用卸载清除 |
| 共享媒体 | `MediaStore` | Android 10 起推荐通过 MediaStore 访问 |

Android 10（API 29）引入分区存储，Android 11 起强制执行。应用应优先使用内部私有目录和外部私有目录，避免直接拼接外部存储路径。

### 1.2 IO 的类型

* 顺序读写与随机读写：顺序读写吞吐高，随机读写延迟高，数据库和 mmap 更依赖随机访问能力。
* 缓冲 IO 与直接 IO：缓冲 IO 经过内核页缓存，直接 IO 绕过页缓存，应用通常使用缓冲 IO。
* 阻塞与非阻塞：普通 `InputStream`/`OutputStream` 是阻塞的，NIO 的 `Channel` 支持非阻塞和就绪通知。
* 同步与异步：同步调用要等 IO 完成才返回，异步通过回调或 Future 通知结果。

### 1.3 页缓存与 fsync

Linux 的 `write()` 通常只把数据拷贝到内核页缓存就返回，真正的落盘由内核后台回写线程完成。这样吞吐高，但进程崩溃或设备断电时，尚未回写的数据可能丢失。需要保证持久化时要调用 `fsync()`：

```java
try (FileOutputStream fos = new FileOutputStream(file)) {
    fos.write(data);
    fos.getFD().sync(); // 强制落盘，代价较高
}
```

## 2 Buffer 与流式读写

### 2.1 为什么需要 Buffer

每调用一次 `read()` 或 `write()` 都可能触发一次系统调用，用户态和内核态之间的切换开销远大于数据拷贝本身。缓冲区可以把多次小 IO 合并成少量大 IO，显著降低系统调用次数。

### 2.2 使用缓冲流

```java
try (BufferedInputStream in = new BufferedInputStream(new FileInputStream(src));
     BufferedOutputStream out = new BufferedOutputStream(new FileOutputStream(dst))) {
    byte[] buffer = new byte[8 * 1024];
    int len;
    while ((len = in.read(buffer)) != -1) {
        out.write(buffer, 0, len);
    }
}
```

缓冲区不是越大越好：太小系统调用多，太大占用内存、增加 GC 压力。通常选择 4KB、8KB、32KB 或 64KB，与文件系统块大小和业务吞吐匹配。

### 2.3 大文件流式处理

不要把大文件一次性读入内存，否则容易 OOM。应该分块读取、边读边处理，图片、视频、日志等大文件都适合这种方式，必要时配合临时文件和断点续传。

## 3 Okio

### 3.1 核心概念

Okio 是 Square 开源的 IO 库：

* `Source` / `Sink`：轻量的可读/可写数据源，类似 `InputStream` / `OutputStream`。
* `Buffer`：由多个 `Segment` 组成的双向链表，读写共享同一块内存，减少拷贝。
* `ByteString`：不可变的字节序列，适合做键、摘要和协议字段。
* `Timeout`：统一的超时控制，支持同步和异步超时。

### 3.2 示例

```java
// 读取文本
BufferedSource source = Okio.buffer(Okio.source(file));
try {
    String content = source.readUtf8();
} finally {
    source.close();
}
```

Okio 的 Segment 会池化复用，读写之间传递 `Buffer` 只移动指针，避免数据拷贝；它还支持 gzip、哈希和超时，适合网络和文件场景。

## 4 文件读写最佳实践

### 4.1 选择合适的目录

* 配置和用户数据放在 `getFilesDir()`，不要放在 `getCacheDir()`，后者可能被系统清理。
* 临时文件和缓存图片放在 `getCacheDir()`，并做好容量控制和过期清理。
* 需要用户可见的媒体文件通过 `MediaStore` 写入，不要直接写外部存储根目录。

### 4.2 原子写

直接覆盖写文件时，如果写到一半进程被杀，文件会损坏。推荐先写临时文件，`fsync` 后再重命名：

```java
File tmp = new File(file.getParentFile(), file.getName() + ".tmp");
try (FileOutputStream fos = new FileOutputStream(tmp)) {
    fos.write(data);
    fos.getFD().sync();
}
if (!tmp.renameTo(file)) {
    file.delete();
    tmp.renameTo(file);
}
```

同一文件系统内的 `rename` 是原子操作，可以保证读到的要么是旧文件，要么是新文件。资源必须用 try-with-resources 及时关闭，否则会泄漏文件描述符，最终导致 `Too many open files`。

### 4.3 随机读写与 mmap

需要随机访问大文件时，可以使用 `RandomAccessFile` 定位读写，也可以把文件映射到内存（mmap）。mmap 的读写由缺页中断驱动，适合大文件随机访问和只读索引，但映射区域会占用虚拟内存，释放时机不易控制。

### 4.4 异步与批量

* 所有磁盘 IO 都应该在子线程执行，主线程只处理结果。
* 高频小写入先在内存中聚合，达到阈值或页面退出时批量落盘。
* 使用单线程串行写日志，避免多线程竞争文件锁。

## 5 SharedPreferences 与 MMKV

### 5.1 SharedPreferences 的问题

* 首次访问时会在主线程**一次性加载整个 XML 文件**到内存，文件越大越慢。
* `commit()` 同步写磁盘并返回结果，在主线程调用会阻塞。
* `apply()` 异步写磁盘，但 `QueuedWork` 会在 `onPause()`、`onStop()` 等时机等待写入完成，频繁调用仍可能卡顿。
* 多进程访问不安全，容易出现数据覆盖；也不适合存储大 JSON、列表等大对象。

### 5.2 MMKV

MMKV（`com.tencent:mmkv`）是微信开源的键值存储组件，核心原理是 **mmap + protobuf + 增量写入**：通过 mmap 把文件映射到内存，读写直接操作内存，由内核负责回写；使用 protobuf 编码并支持增量更新，不需要每次全量序列化；支持多进程模式。

```java
MMKV.initialize(context); // Application 中初始化一次

MMKV kv = MMKV.defaultMMKV();
kv.encode("user_id", 1001L);
long userId = kv.decodeLong("user_id", 0);

// 多进程模式
MMKV multi = MMKV.mmkvWithID("account", MMKV.MULTI_PROCESS_MODE);
```

### 5.3 选型对比

| 方案 | 写入方式 | 多进程 | 适合场景 |
| --- | --- | --- | --- |
| SharedPreferences | XML，apply 异步/commit 同步 | 不安全 | 少量配置、低频写入 |
| MMKV | mmap + protobuf，增量写 | 支持 | 高频读写、多进程 |
| DataStore | 协程/Flow，事务式 | 不支持 | 新项目、类型安全 |

## 6 数据库批量操作

### 6.1 使用事务

每条 SQL 自动提交时，SQLite 会为每条语句执行一次 fsync。批量插入应该包在一个事务里：

```java
SQLiteDatabase db = helper.getWritableDatabase();
db.beginTransaction();
try {
    for (User user : users) {
        db.insert("user", null, toContentValues(user));
    }
    db.setTransactionSuccessful();
} finally {
    db.endTransaction();
}
```

事务可以把多次写入合并为一次提交，性能提升往往有一个数量级。

### 6.2 预编译语句

使用 `SQLiteStatement` 复用编译结果，避免重复解析 SQL：

```java
SQLiteStatement stmt = db.compileStatement(
        "INSERT INTO user(name, age) VALUES(?, ?)");
db.beginTransaction();
try {
    for (User user : users) {
        stmt.bindString(1, user.name);
        stmt.bindLong(2, user.age);
        stmt.executeInsert();
    }
    db.setTransactionSuccessful();
} finally {
    db.endTransaction();
}
```

### 6.3 WAL 与索引

WAL（Write-Ahead Logging）把写操作先写入日志文件，读操作不阻塞写操作，适合读写并发：

```java
db.enableWriteAheadLogging();
```

Room 在非低内存设备上默认使用 WAL。开启后数据库目录会多出 `-wal` 和 `-shm` 文件，备份和迁移时要注意。查询方面，为 `WHERE`、`JOIN`、`ORDER BY` 中的列建立索引，避免 `SELECT *`，用 `EXPLAIN QUERY PLAN` 检查是否走索引，并分页加载。

## 7 日志与序列化对 IO 的影响

### 7.1 日志

* 每条日志都会通过 socket 写入 logd，频繁打印会造成系统调用和锁竞争。
* 不要在循环中打印日志，尤其是大字符串和 JSON；Release 包关闭调试日志。
* 文件日志使用单线程异步写入，批量 flush，并限制文件大小和数量。

### 7.2 序列化与压缩

* JSON 可读性好，但体积大、解析慢，不适合大数据量和高频场景。
* Protobuf、FlatBuffers 等二进制格式体积小、解析快，适合网络传输和本地存储。
* Java 的 `Serializable` 会写入大量元数据，性能和体积都不占优，不建议用于持久化。
* 文本日志、JSON 可以用 gzip 压缩后落盘或上传；图片、视频等已压缩数据不要再压缩。

## 8 StrictMode 检测

StrictMode 可以在调试包中捕获主线程的磁盘读写、网络访问和资源泄漏：

```java
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(new StrictMode.ThreadPolicy.Builder()
            .detectDiskReads()
            .detectDiskWrites()
            .detectNetwork()
            .penaltyLog()
            .build());

    StrictMode.setVmPolicy(new StrictMode.VmPolicy.Builder()
            .detectLeakedClosableObjects()
            .penaltyLog()
            .build());
}
```

* 只在 Debug 包开启，Release 包关闭，避免性能损耗和误报。
* `penaltyLog()` 输出日志，`penaltyDeath()` 会让应用直接崩溃，适合本地排查。
* 关注 `StrictMode policy violation` 日志中的堆栈，定位具体的文件和调用点。
* StrictMode 主要暴露主线程 IO，子线程的低效 IO 需要结合 Perfetto、`strace` 等工具分析。

## 9 总结

* IO 优化的核心是减少系统调用、减少数据拷贝、避免主线程阻塞。
* 使用缓冲流和流式读写处理大文件，必要时使用 Okio、mmap 或 NIO。
* 文件写入要保证原子性，重要数据在合适的时机 `fsync`。
* SharedPreferences 适合少量配置，高频读写和多进程场景优先考虑 MMKV 或 DataStore。
* 数据库批量操作使用事务和预编译语句，读写并发场景开启 WAL。
* 日志和序列化是容易被忽视的 IO 来源，Release 包要控制输出。
