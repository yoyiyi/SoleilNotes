## 1 一次网络请求的成本

移动网络下，一次请求的代价远不止流量。射频模块从空闲被唤醒、建立连接、传输数据，再到回落，整个过程都有功耗：

| RRC 状态 | 功耗 | 说明 |
| --- | --- | --- |
| Idle | 低 | 无连接，仅监听寻呼 |
| Connected | 高 | 持续收发数据，射频全功率 |
| Tail | 中高 | 请求结束后仍保持数秒到十几秒才回落 |

这意味着**频繁的小请求比一次大请求更耗电**。优化的基本思路是：合并请求、做好缓存、减少轮询、缩短连接建立时间。

## 2 连接复用与 HTTP/2

### 2.1 为什么要复用连接

一次 HTTPS 请求包含 TCP 三次握手和 TLS 握手，在弱网下可能消耗几百毫秒甚至数秒。如果每个请求都新建连接，不仅慢，还会反复唤醒射频。

OkHttp 通过 `ConnectionPool` 复用连接：请求结束后连接进入空闲池，后续同源请求直接复用。

```kotlin
val client = OkHttpClient.Builder()
    .connectionPool(ConnectionPool(5, 5, TimeUnit.MINUTES)) // 最多 5 个空闲连接，保活 5 分钟
    .build()
```

* 默认就是 5 个空闲连接、5 分钟保活，通常不需要修改。
* 连接池按 `Address`（协议、主机、端口、代理等）复用，不同域名不会共享连接。
* 全局共享一个 `OkHttpClient` 实例，不要每次请求都 new，否则连接池和线程池都失去意义。

### 2.2 HTTP/2

HTTP/2 在一条 TCP 连接上**多路复用**多个请求，避免了 HTTP/1.1 的队头阻塞，同时使用 HPACK 压缩请求头：

* 二进制分帧，同一连接上并发多个 stream。
* 头部压缩，重复的 header 只传增量。
* 服务端可主动推送（实际使用较少）。
* 一条连接即可承载多个并发请求，减少握手与射频唤醒。

OkHttp 在 TLS 连接上通过 ALPN 自动协商 h2，无需手动配置协议列表；明文 `http://` 默认仍走 HTTP/1.1，除非使用 `Protocol.H2_PRIOR_KNOWLEDGE`（要求服务端支持 h2c）。HTTP/2 需要服务端或 CDN 开启，客户端无法单方面获益。

## 3 DNS 优化

### 3.1 系统 DNS 的问题

系统 DNS 走 UDP 53 端口，请求运营商的 Local DNS：

* 可能被劫持或污染，返回错误 IP。
* 解析结果受运营商调度影响，可能分配到较远的节点。
* 首次解析耗时不可控，弱网下可能达到数秒。
* TTL 缓存由系统管理，应用无法干预。

### 3.2 HTTPDNS

HTTPDNS 通过 HTTP 接口向权威 DNS 服务查询域名的 IP，绕过 Local DNS：

* 防劫持、防污染，返回结果更可信。
* 可以拿到离用户更近的节点 IP，提升速度。
* 应用可以自己控制缓存与降级策略。
* 注意：HTTPS 的证书校验和 SNI 仍然使用域名，OkHttp 的 `Dns` 只负责把域名解析成 IP，URL 仍是域名，因此不需要手动改 Host。

```kotlin
object HttpDns : Dns {
    override fun lookup(hostname: String): List<InetAddress> {
        val ip = HttpDnsClient.getIp(hostname) // 带本地缓存与 TTL
        return if (ip != null) listOf(InetAddress.getByName(ip))
        else Dns.SYSTEM.lookup(hostname)      // 失败兜底
    }
}

val client = OkHttpClient.Builder().dns(HttpDns).build()
```

使用要点：

* 必须保留系统 DNS 兜底，HTTPDNS 服务不可用时不能导致所有请求失败。
* 缓存要遵循 TTL，并在网络切换时失效。
* 支持 IPv6，返回多个 IP 时可由 OkHttp 做失败切换。
* 减少域名数量、启动时预解析关键域名，也能明显缩短首屏请求时间。

## 4 请求合并与缓存

### 4.1 请求合并

* 把多个小请求合并成批量接口，例如一次拉取多个用户信息。
* 同一时刻的相同请求做去重，共享同一个结果（OkHttp 不会自动合并，需要在业务层用 `Deferred` 或拦截器实现）。
* 输入框搜索等场景做 debounce，停止输入 300ms 后再发请求。
* 非实时操作用队列攒批，例如埋点、日志上报。

### 4.2 HTTP 缓存

| 响应头 | 作用 |
| --- | --- |
| `Cache-Control: max-age=3600` | 资源在 1 小时内新鲜，可直接用本地缓存 |
| `Cache-Control: no-cache` | 可以缓存，但每次使用前必须协商 |
| `Cache-Control: no-store` | 完全不缓存 |
| `Cache-Control: private` | 只允许客户端缓存，不允许代理缓存 |
| `ETag` / `If-None-Match` | 协商缓存，内容未变返回 304 |
| `Last-Modified` / `If-Modified-Since` | 按修改时间协商 |

OkHttp 内置了 HTTP 缓存，只需指定缓存目录和大小：

```kotlin
val cache = Cache(File(context.cacheDir, "http_cache"), 50L * 1024 * 1024)
val client = OkHttpClient.Builder().cache(cache).build()
```

* 只缓存 GET 请求，POST 默认不缓存。
* 304 响应没有 body，OkHttp 会自动复用本地缓存，节省流量。
* `no-cache` 不是"不缓存"，而是"每次都要协商"，不要混淆。
* 业务层还可以叠加内存 `LruCache`、磁盘缓存和过期时间，形成多级缓存；注意处理缓存穿透与雪崩。

## 5 弱网、超时与重试

### 5.1 超时设置

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| `connectTimeout` | 10s | 建立 TCP 连接 |
| `readTimeout` | 15s | 等待响应数据 |
| `writeTimeout` | 15s | 发送请求体 |
| `callTimeout` | 30s | 整个请求的上限，含重试与重定向 |

弱网下不要无限等待，也不要设置得过短导致正常请求被误杀。`callTimeout` 是兜底，防止个别请求永远挂起。

### 5.2 重试策略

* `retryOnConnectionFailure(true)` 会在连接失败时尝试其他路由/IP；对已经发出的非幂等请求，业务层不要盲目重试。
* 业务层只对**幂等**请求重试（GET、PUT、DELETE）；POST 重试需要服务端支持幂等键。
* 使用指数退避，必要时加随机抖动，避免雪崩：1s、2s、4s……上限 30s。

```kotlin
suspend fun <T> retry(times: Int = 3, block: suspend () -> T): T {
    var delayMs = 1000L
    repeat(times) { i ->
        try {
            return block()
        } catch (e: IOException) {
            if (i == times - 1) throw e
            delay(delayMs)
            delayMs = (delayMs * 2).coerceAtMost(30_000L)
        }
    }
    error("unreachable")
}
```

### 5.3 弱网检测

* 用 `ConnectivityManager` 与 `NetworkCapabilities` 判断是否联网、是否计费网络、是否经过验证（`NET_CAPABILITY_VALIDATED`）。
* 网络切换时取消无意义的请求，避免在断网状态下反复重试。
* 弱网下降低图片质量、减少预加载，优先保证核心接口。

## 6 数据压缩

* **gzip**：文本压缩率高，OkHttp 会自动添加 `Accept-Encoding: gzip` 并透明解压；如果手动设置该头，就需要自己解压。
* **brotli（br）**：比 gzip 再小 15%~25%，需要服务端支持，客户端引入 `okhttp-brotli` 并添加 `BrotliInterceptor`。
* **请求体压缩**：大 JSON 请求可以用 gzip 包装 `RequestBody`，但要与服务端约定。
* **二进制协议**：Protobuf、FlatBuffers 通常比 JSON 更小、解析更快。
* **图片**：优先 WebP/AVIF，按展示尺寸下发，不要传原图。
* 已经压缩过的图片、zip、视频不要再 gzip，收益接近零却增加 CPU 开销。

```kotlin
val client = OkHttpClient.Builder()
    .addInterceptor(BrotliInterceptor())
    .build()
```

## 7 图片加载

图片往往是流量大头，优化重点是"不下不需要的图、不下超过需要的尺寸"：

```kotlin
Glide.with(context)
    .load(url)
    .override(300, 300) // 按 View 尺寸解码，避免加载原图
    .diskCacheStrategy(DiskCacheStrategy.AUTOMATIC)
    .placeholder(R.drawable.placeholder)
    .into(imageView)
```

* 列表滑动时 `Glide.with(context).pauseRequests()`，停止后再 `resumeRequests()`。
* 使用缩略图先展示，点击后再加载高清图。
* 服务端支持按参数裁剪、选择格式（WebP/AVIF）。
* 预加载只做下一页，不要一次性下载全部图片。
* 大图上传前先压缩、裁剪，避免把几 MB 的原图直接发出去。

## 8 流量与电量的权衡

| 策略 | 流量 | 电量 | 实时性 |
| --- | --- | --- | --- |
| 实时请求 | 高 | 高 | 最好 |
| 短轮询 | 很高 | 很高 | 一般 |
| 长连接 / 推送 | 低 | 低 | 好 |
| 批量 + 缓存 | 低 | 低 | 可接受 |

* 大文件下载、资源更新等到 Wi-Fi 或非计费网络再执行，判断 `NET_CAPABILITY_NOT_METERED`。
* 尊重系统的流量节省模式（Data Saver），不要在后台大量预取。
* 后台任务用 `WorkManager` / `JobScheduler` 加约束（充电、Wi-Fi、空闲），不要用 `AlarmManager` 轮询。
* 页面退出后取消无用请求，避免后台继续耗电。

## 9 OkHttp 常用优化配置

```kotlin
val client = OkHttpClient.Builder()
    .connectionPool(ConnectionPool(5, 5, TimeUnit.MINUTES))
    .dispatcher(Dispatcher().apply {
        maxRequests = 64
        maxRequestsPerHost = 5
    })
    .connectTimeout(10, TimeUnit.SECONDS)
    .readTimeout(15, TimeUnit.SECONDS)
    .writeTimeout(15, TimeUnit.SECONDS)
    .callTimeout(30, TimeUnit.SECONDS)
    .retryOnConnectionFailure(true)
    .cache(Cache(File(context.cacheDir, "http_cache"), 50L * 1024 * 1024))
    .dns(HttpDns)
    .addInterceptor(HeaderInterceptor())   // 应用拦截器：公共参数、签名
    .addNetworkInterceptor(StatsInterceptor()) // 网络拦截器：统计真实流量
    .eventListener(NetworkEventListener()) // 分阶段耗时监控
    .build()
```

配置说明：

* **全局单例**：整个应用共享一个 `OkHttpClient`，连接池、线程池、缓存才能复用。
* **Dispatcher**：控制并发总数与单 Host 并发，避免大量请求同时抢占带宽。
* **超时**：按业务设置，下载大文件可以单独用一个放宽 `readTimeout` 的客户端。
* **缓存**：GET 接口配合服务端 `Cache-Control` 才能生效。
* **拦截器**：应用拦截器只调用一次，网络拦截器会包含重定向与重试，统计流量要用后者。
* **证书校验**：不要为了"兼容"实现 trust-all，会带来中间人攻击风险。

## 10 监控指标

* 分阶段耗时：DNS、TCP 连接、TLS 握手、TTFB、下载。
* 成功率、HTTP 状态码分布、超时率、重试率。
* 请求与响应字节数、缓存命中率、压缩率。
* 按网络类型（Wi-Fi、4G、5G、弱网）和地域维度拆分。
* 线上通过 OkHttp `EventListener` 采样上报，避免监控本身成为负担。
