## 1 存储方式概览

Android 提供了多种数据存储方式，选择哪一种，取决于**数据量、读写频率、是否需要查询、是否跨进程、是否敏感**这几个维度：

| 方式 | 典型场景 | 优点 | 缺点 |
| --- | --- | --- | --- |
| SharedPreferences | 少量键值配置、开关 | 使用简单、系统原生 | 全量写文件、主线程风险、不支持多进程 |
| MMKV | 高频键值读写、多进程 | mmap 写入快、支持多进程 | 第三方库、文件格式私有 |
| DataStore | 新项目的键值/对象配置 | 协程异步、事务性、类型安全 | 只支持单进程、API 较新 |
| 文件 | 日志、图片、大 JSON、缓存 | 灵活、无大小限制 | 无查询能力、需自己管理并发 |
| SQLite / Room | 结构化数据、列表、搜索 | 支持索引、事务、复杂查询 | 需设计表结构、有学习成本 |

常见的误区是"什么都塞 SharedPreferences"：把用户列表、缓存 JSON、历史记录都存成字符串，每次读写都要序列化整个大对象。**配置用键值存储，结构化数据用数据库，大块二进制用文件**，是基本的分工原则。

## 2 SharedPreferences 的 apply 与 commit

### 2.1 实现原理

SharedPreferences 的本质是**一个内存中的 Map + 一个 XML 文件**：

* 首次调用 `getSharedPreferences()` 时，`SharedPreferencesImpl` 会在后台线程把 XML 全量解析进内存；解析完成之前，任何 `getXxx()` 都会阻塞等待（`awaitLoadedLocked`），所以**第一次读取仍然可能卡主线程**。
* `commit()` / `apply()` 都先改内存中的 Map，再把**整个 XML 文件重新写一遍**。文件越大、写入越频繁，成本越高。
* 每个进程各持有一份 Map 与文件，互相覆盖是常态，因此 **SharedPreferences 不支持多进程**。

### 2.2 apply 与 commit 的差异

| 对比项 | apply() | commit() |
| --- | --- | --- |
| 磁盘写入 | 异步，交给 QueuedWork 单线程队列 | 同步，在当前线程写文件 |
| 返回值 | void，无法得知成败 | boolean，返回是否写入成功 |
| 主线程耗时 | 通常很短，但排队任务会被等待 | 直接阻塞，文件大时明显 |
| 适用场景 | 绝大多数 UI 场景 | 必须确认落盘、退出前保存 |

```java
SharedPreferences sp = getSharedPreferences("settings", MODE_PRIVATE);
boolean saved = sp.edit().putString("token", token).commit(); // 同步写盘
sp.edit().putString("token", token).apply();                  // 异步写盘
```

### 2.3 apply 的 ANR 风险

`apply()` 本身是异步的，但系统在 **Activity.onStop、Service 处理结束、BroadcastReceiver.onReceive 结束**等时机，会调用 `QueuedWork.waitToFinish()` 等待未完成的 apply 任务落盘。如果队列积压了大量写入，或者单个 XML 很大，主线程就会被阻塞，严重时触发 ANR。

典型踩坑场景：

* 在 `onPause()` 里连续 `apply()` 十几次（埋点、状态、时间戳分开写）。
* 把几百 KB 的 JSON 字符串塞进一个 key，每次 apply 都重写整个文件；或主线程高频调用 apply（如列表滚动时实时记录位置）。

优化手段：

* **合并写入**：一次 `edit()` 里 put 多个 key，只产生一次磁盘写。
* **控制文件大小**：单个 SP 文件建议保持在几十 KB 以内，大对象改用文件或数据库。
* **避免高频写**：位置、播放进度等用内存变量暂存，按秒或按页面退出时再落盘。
* **写操作放子线程**：`commit()` 在子线程调用同样安全，不要在主线程等结果。
* 只有确实需要"写完才能继续"（如退出登录清理 token）时才用 `commit()`；同一个 `edit()` 只提交一次，不要 apply 与 commit 混用。

使用建议：使用 `MODE_PRIVATE`（`MODE_WORLD_READABLE/WRITEABLE` 在 API 17 起废弃，Android 7.0 起使用会抛异常）；不要用 SP 存 token、密码等敏感信息；多进程场景改用 MMKV，或把数据收敛到单一进程通过 Binder 访问。

## 3 MMKV

### 3.1 原理

MMKV 是微信开源的键值存储组件，核心是 **mmap 内存映射 + protobuf 编码**：

* 通过 `mmap` 把文件映射到进程虚拟内存，读写直接操作内存，不需要每次都 `write()`，由内核负责页的换入换出。
* 使用 protobuf 对键值做增量编码，**追加写**而不是全量重写，写入成本与已有数据量基本无关。
* 通过文件锁加增量日志支持多进程模式（`MMKV.MULTI_PROCESS_MODE`），文件中的有效性标记保证异常退出后能回滚到最后一个完整状态。

### 3.2 基本使用

```kotlin
// Application.onCreate 中初始化，只需一次
MMKV.initialize(this)

val kv = MMKV.defaultMMKV()                                    // 单进程默认实例
val multi = MMKV.mmkvWithID("account", MMKV.MULTI_PROCESS_MODE) // 多进程

kv.encode("token", "abc")
kv.encode("launch_count", 3)
val token = kv.decodeString("token", "")
kv.removeValueForKey("token")
```

### 3.3 与 SharedPreferences 的对比

| 对比项 | SharedPreferences | MMKV |
| --- | --- | --- |
| 写入方式 | 全量重写 XML | mmap + 增量追加 |
| 单次写入耗时 | 随文件增大而增大 | 基本恒定 |
| 多进程 | 不支持 | 支持（需显式开启） |
| 数据格式 | XML 明文 | 二进制（默认非加密） |

从 SharedPreferences 迁移时，先把旧数据读出写入 MMKV，再删除旧文件；迁移要在**单进程、单线程**下完成，并保证幂等，避免重复迁移覆盖新数据。

## 4 Jetpack DataStore

DataStore 是 Google 推出的 SharedPreferences 替代方案，基于 **Kotlin 协程 + Flow**，读写全部异步，更新操作是**事务性**的（读-改-写在一个事务中完成，不会并发覆盖）。

```kotlin
private val Context.dataStore: DataStore<Preferences> by preferencesDataStore(name = "settings")
private val TOKEN = stringPreferencesKey("token")

// 读：返回 Flow，UI 层 collect，IO 异常时降级为空配置
val tokenFlow: Flow<String> = context.dataStore.data
    .catch { e -> if (e is IOException) emit(emptyPreferences()) else throw e }
    .map { prefs -> prefs[TOKEN] ?: "" }

// 写：挂起函数，内部切到 IO 线程
suspend fun saveToken(token: String) {
    context.dataStore.edit { prefs -> prefs[TOKEN] = token }
}
```

配置项较多、希望类型安全时，可以使用 Proto DataStore：用 protobuf 定义数据结构，实现 `Serializer<Settings>` 的 `readFrom`/`writeTo`，再通过 `dataStore(fileName = "settings.pb", serializer = ...)` 创建。

注意事项：

* DataStore **只支持单进程**（同一文件被多个进程或多次创建实例会抛异常），首次读取是懒加载，读大文件时不要在主线程 `runBlocking`。
* 从 SharedPreferences 迁移使用 `SharedPreferencesMigration`，迁移完成后旧文件会被删除。
* DataStore 适合"读多写少"的配置；高频写入仍建议内存缓存 + 定期落盘。

## 5 文件存储与序列化

### 5.1 文件 API 的选择

| 目录 | API | 特点 |
| --- | --- | --- |
| 内部私有 | `getFilesDir()` / `getDir()` | 随应用卸载删除，其他应用不可见 |
| 内部缓存 | `getCacheDir()` | 空间不足时可能被清理，不要存重要数据 |
| 外部私有 | `getExternalFilesDir(type)` | 随卸载删除，Android 4.4+ 无需存储权限 |
| 外部缓存 | `getExternalCacheDir()` | 可被系统与用户清理 |
| 共享媒体 | `MediaStore` | 图片/视频/音频写入相册，需适配分区存储 |
| 用户选择 | SAF（`ACTION_OPEN_DOCUMENT`） | 由用户授权任意目录，无需全盘权限 |

外部存储可能不可用（未挂载、被移除），使用前必须判空并捕获 `IOException`；重要数据一律放内部存储。写文件时**先写临时文件、`fsync` 后再原子重命名**，避免写到一半进程被杀导致文件损坏。

### 5.2 序列化格式对比

| 格式 | 体积 | 解析速度 | 可读性 | 适用场景 |
| --- | --- | --- | --- | --- |
| JSON | 大 | 中等 | 好 | 接口传输、调试、配置 |
| Protobuf | 小（通常比 JSON 小 30%~70%） | 快 | 差（需 schema） | 本地缓存、上报、RPC |
| FlatBuffers | 小 | 极快（零拷贝） | 差 | 游戏、频繁读取的大对象 |

JSON 在 Android 上常用 Gson、Moshi、kotlinx.serialization，其中后两者支持编译期生成适配器，避免反射带来的启动开销和混淆问题：

```kotlin
// kotlinx.serialization：编译期生成，无需反射
@Serializable
data class User(val id: Long, val name: String, val tags: List<String> = emptyList())
val json = Json { ignoreUnknownKeys = true }
val text = json.encodeToString(User(1, "soleil"))
val user = json.decodeFromString<User>(text)
```

选择建议：

* 与服务端交互、需要人眼排查：**JSON**。
* 本地缓存结构化数据、日志上报、对体积敏感：**Protobuf**（需要 `.proto` 与 protobuf 插件）。
* 单机大数据、频繁随机读取、对延迟极敏感：**FlatBuffers**。
* 不要用 Java 原生 `Serializable` 做持久化：体积大、速度慢，`serialVersionUID` 不匹配还会直接失败。

## 6 数据库与文件的取舍

| 维度 | SQLite / Room | 文件 |
| --- | --- | --- |
| 结构化查询 | 支持 SQL、索引、聚合 | 需自己遍历 |
| 事务与一致性 | 支持 | 需自己保证 |
| 部分更新 | 支持（UPDATE 单行） | 通常要重写整个文件 |
| 大数据量 | 支持分页、按需加载 | 需自己切分 |
| 二进制大对象 | 不推荐（大 BLOB 影响性能） | 推荐 |

判断标准：

* 数据需要**按条件查询、排序、分页、统计**，或者需要**局部更新** → 数据库。
* 数据是**整体读写的大块内容**（图片、音频、导出文件、日志） → 文件。
* 数据量很小（几十个 key） → 键值存储（DataStore / MMKV）。
* 图片不要存数据库 BLOB，存文件，数据库只存路径。

## 7 存储位置：内部与外部

| 对比项 | 内部存储 | 外部存储 |
| --- | --- | --- |
| 路径 | `/data/data/<pkg>/` | `/sdcard/Android/data/<pkg>/` 或共享目录 |
| 权限 | 无需申请 | 私有目录无需权限，共享目录需媒体权限 |
| 可见性 | 仅本应用（root 除外） | 用户与其他应用可访问 |
| 卸载 | 删除 | 私有目录删除，共享目录保留 |
| 可靠性 | 高 | 可能被拔卡、被清理 |
| 空间 | 通常较小 | 通常较大 |

`filesDir`、`cacheDir`、`getExternalFilesDir()` 分别对应上表目录；写入前用 `File.usableSpace` 检查剩余空间，避免写满磁盘。

Android 10（API 29）引入分区存储，Android 11（API 30）起强制生效：

* 应用只能直接访问自己的私有目录，以及通过 `MediaStore` 授权的媒体文件；`Environment.getExternalStorageDirectory()` 已废弃，保存到相册用 `MediaStore` + `openOutputStream`。
* `MANAGE_EXTERNAL_STORAGE` 属于特殊权限，上架 Google Play 需说明用途，非必要不要申请。

## 8 备份与权限

### 8.1 备份配置

Android 6.0 起支持自动备份（Auto Backup），默认开启，备份到用户的云端，单个应用限额 25MB。从 API 31 起使用 `dataExtractionRules`，低版本仍读 `fullBackupContent`：

```xml
<application
    android:allowBackup="true"
    android:fullBackupContent="@xml/backup_rules"
    android:dataExtractionRules="@xml/data_extraction_rules">
</application>
```

```xml
<!-- res/xml/backup_rules.xml（API 23~30）：只备份配置，排除设备标识与缓存库 -->
<full-backup-content>
    <include domain="sharedpref" path="settings.xml" />
    <exclude domain="sharedpref" path="device.xml" />
    <exclude domain="database" path="cache.db" />
</full-backup-content>
```

API 31+ 的 `data_extraction_rules.xml` 结构类似，分为 `cloud-backup` 与 `device-transfer` 两段，规则写法相同。

注意：

* `allowBackup="false"` 可以彻底关闭备份，但会影响换机迁移；设备标识、token、一次性状态等**不应备份**，否则换机后会出现"幽灵登录"或重复推送。
* 备份规则写错不会导致编译失败，但会静默失效，建议在测试机上用 `bmgr` 验证。

### 8.2 敏感数据与权限

* SharedPreferences、MMKV、数据库默认都是**明文**，root 设备或备份文件可被读取；可以用 Jetpack Security 的 `EncryptedSharedPreferences` 快速接入，也可以直接用 Keystore 派生密钥后自行加密（AES-GCM），或引入 Tink。
* 密钥不要硬编码在代码或 gradle 中，服务端下发的密钥要有轮换机制；加密只保护"静态数据"，内存中的明文、日志、崩溃堆栈仍可能泄漏，日志脱敏同样重要。

| 权限 | 适用版本 | 说明 |
| --- | --- | --- |
| `READ_EXTERNAL_STORAGE` | API ≤ 32 | Android 13 起被媒体细分权限替代 |
| `WRITE_EXTERNAL_STORAGE` | API ≤ 28 | Android 10 起对分区存储无效 |
| `READ_MEDIA_IMAGES/VIDEO/AUDIO` | API 33+ | 读取共享媒体 |
| `READ_MEDIA_VISUAL_USER_SELECTED` | API 34+ | 用户仅授权部分照片 |
| `MANAGE_EXTERNAL_STORAGE` | API 30+ | 特殊权限，需应用商店审核 |

权限申请遵循最小化原则：能用自己的私有目录就不要申请存储权限，能用 SAF 就不要申请全盘权限。

## 9 数据存储优化清单

* 键值配置优先 DataStore；高频、多进程场景用 MMKV；SharedPreferences 合并写入、控制文件大小、避免主线程高频 apply。
* 大对象不要塞进键值存储；结构化数据用 Room 并建立索引，图片/音频/日志等大文件存文件系统，数据库只存路径。
* 序列化优先编译期方案（kotlinx.serialization / Moshi codegen / Protobuf），写文件用"临时文件 + 原子重命名"并 `fsync`。
* 敏感数据加密存储，备份规则排除设备相关与一次性凭证；适配分区存储，不申请非必要的存储权限。
* 定期清理缓存目录并设置容量上限，监控存储相关的 ANR、IO 耗时与磁盘占用。
