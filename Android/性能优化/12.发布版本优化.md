## 1 debug 与 release 的差异

debug 包为了可调试、可断点、编译快，几乎关闭了所有优化；release 包才代表用户真正拿到的版本。两者差异远不止一个 `debuggable` 开关：

| 维度 | debug | release |
| --- | --- | --- |
| `debuggable` | true | false |
| 代码压缩/混淆 | 关闭 | R8 开启 |
| 资源压缩 | 关闭 | `shrinkResources` 开启 |
| 签名 | debug.keystore | 正式 keystore |
| 日志 | 全量输出 | 关闭或降级 |
| 性能 | 较慢，含调试信息 | 较快，R8 优化 |
| 崩溃栈 | 可直接定位 | 需 mapping 还原 |
| 环境 | 测试/预发 | 生产 |

因此**不要用 debug 包做性能测试**，也不要把 debug 包发给用户。线上包必须满足：`debuggable=false`、R8 开启、资源压缩开启、正式签名、日志关闭、崩溃监控可用。

## 2 release 构建配置

以 Kotlin DSL 为例，一个典型的 release 配置：

```kotlin
android {
    buildTypes {
        release {
            isMinifyEnabled = true          // 开启 R8 代码压缩/混淆/优化
            isShrinkResources = true        // 移除无用资源，依赖 minify
            isDebuggable = false
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
            signingConfig = signingConfigs.getByName("release")
            ndk {
                abiFilters += listOf("arm64-v8a", "armeabi-v7a")
            }
        }
    }
}
```

要点：

* `minifyEnabled` 打开后，R8 会做裁剪（shrink）、混淆（obfuscate）、优化（optimize）。
* `shrinkResources` 必须在 `minifyEnabled` 为 true 时才有意义，它依赖 R8 分析出的无用代码，再移除这些代码引用的资源。
* `abiFilters` 只保留真实需要的 ABI，能显著减小包体积。

## 3 R8 与 ProGuard 规则

### 3.1 R8 做了什么

R8 是 ProGuard 的替代品，集成在 AGP 中，开启 `minifyEnabled` 即生效：

* **Shrinking**：删除未被引用的类、方法、字段。
* **Optimization / Obfuscation**：内联、常量折叠、删除无用分支，并把类名、方法名、字段名改成短名。
* **Dexing**：直接产出 DEX，替代 D8 的部分流程。

AGP 8 起 R8 默认开启 full mode，优化更激进，对反射、JNI、序列化等动态调用的保留规则要求更严格。

### 3.2 常用规则

```proguard
# 保留注解、泛型签名、内部类信息，反射和反序列化依赖它们
-keepattributes *Annotation*,Signature,InnerClasses,EnclosingMethod
# 保留行号，崩溃栈才能还原到源码行
-keepattributes SourceFile,LineNumberTable
# 反射/JSON 使用的模型类
-keep class com.example.model.** { *; }
# Parcelable
-keep class * implements android.os.Parcelable {
    public static final ** CREATOR;
}
# 枚举的 values()/valueOf() 会被反射调用
-keepclassmembers enum * {
    public static **[] values();
    public static ** valueOf(java.lang.String);
}
# WebView JS Bridge
-keepclassmembers class * {
    @android.webkit.JavascriptInterface <methods>;
}
# 不提示第三方库缺失的警告
-dontwarn okhttp3.**
-dontwarn retrofit2.**
```

除了规则文件，也可以直接在类/方法上加 `@Keep`（`androidx.annotation.Keep`），适合少量需要保留的入口。

### 3.3 mapping 文件

release 构建会生成 `app/build/outputs/mapping/release/mapping.txt`，它记录了混淆前后的对应关系：

* 每次发版都要归档 mapping，并与 versionCode 绑定；崩溃平台上传后才能把混淆栈还原成可读代码。
* 不要提交 mapping 到公开仓库，可能泄漏类结构；若需增量混淆，可用 `-applymapping` 复用旧 mapping。

## 4 资源压缩与混淆的坑

### 4.1 资源压缩

开启 `shrinkResources` 后，未被代码引用的资源会被移除。但以下资源是"代码里看不到引用"的，容易被误删：

* 通过 `getIdentifier()`、`getField()` 反射访问的资源，或只在 `AndroidManifest.xml`、`res/xml` 中以字符串形式出现的资源。
* 第三方 SDK 通过资源名查找的资源，以及仅用于动态下发、A/B 实验的资源。

用 `res/raw/keep.xml` 显式保留：

```xml
<resources xmlns:tools="http://schemas.android.com/tools"
    tools:keep="@layout/activity_keep,@drawable/icon_dynamic,@string/remote_title"
    tools:discard="@layout/unused_debug" />
```

`tools:keep` 支持逗号分隔和通配符，`tools:discard` 用于强制删除。每次发版后对比资源数量与包体积，确认没有误删。

### 4.2 常见混淆崩溃

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| JSON 解析字段全为 null | 模型类被混淆，字段名变了 | 保留模型类或使用 `@SerializedName` |
| `ClassNotFoundException` / `NoSuchMethodException` | 反射加载的类或方法被裁剪、改名 | `-keep` / `-keepclassmembers` 对应成员 |
| JNI 崩溃 | native 方法名依赖类名/方法名 | 保留 native 方法所在类 |
| JS 调用无效 | `@JavascriptInterface` 方法被混淆 | keep 该注解的方法 |
| 自定义 View inflate 失败 | 构造函数被裁剪 | 保留 View 的构造函数 |
| Parcelable / 枚举崩溃 | `CREATOR` 或 `values()`/`valueOf()` 被裁剪 | 保留对应字段与方法 |

## 5 分包与多 ABI

### 5.1 Multidex

单个 DEX 的方法数上限是 65536。方法数超限时需要开启 multidex：

```kotlin
android {
    defaultConfig {
        multiDexEnabled = true
    }
}
```

* `minSdk >= 21` 时 ART 原生支持多 DEX，只需开启开关；`minSdk < 21` 时还要继承 `MultiDexApplication` 或在 `attachBaseContext` 中调用 `MultiDex.install(this)`。
* 减少方法数的根本办法是裁剪依赖、开启 R8、避免引入重复功能的大库。

### 5.2 多 ABI

| ABI | 适用设备 | 是否必须 |
| --- | --- | --- |
| `arm64-v8a` | 现代 64 位 ARM 设备 | 必须（Google Play 要求 64 位） |
| `armeabi-v7a` | 老 32 位 ARM 设备 | 按 minSdk 决定 |
| `x86` / `x86_64` | 模拟器、少数平板 | 一般只用于调试 |

```kotlin
android {
    splits {
        abi {
            isEnable = true
            include("arm64-v8a", "armeabi-v7a")
            isUniversalApk = false // 不额外产出全量包
        }
    }
}
```

使用 App Bundle 时，Play 会按设备下发对应的 ABI、语言和密度，无需自己做 splits：

```kotlin
android {
    bundle {
        abi.enableSplit = true
        density.enableSplit = true
        language.enableSplit = true
    }
}
```

注意：多渠道/非 Play 渠道如果只发一个 APK，要保留 `armeabi-v7a` 以兼容老设备；只发 `arm64-v8a` 会丢失一部分用户。

## 6 签名 v1 / v2 / v3 / v4

| 方案 | 引入版本 | 校验范围 | 说明 |
| --- | --- | --- | --- |
| v1（JAR） | Android 1.0 | 部分文件 | 兼容旧系统，API 24 以下只能用它 |
| v2 | Android 7.0（API 24） | 整个 APK | 校验更快，防篡改能力更强 |
| v3 | Android 9.0（API 28） | 整个 APK（含轮换信息） | 换签名密钥时平滑过渡 |
| v4 | Android 11（API 30） | 增量安装 | 生成 `.idsig`，配合 v2/v3 使用 |

AGP 会根据 `minSdk` 自动决定启用哪些方案，也可以显式控制：

```kotlin
signingConfigs {
    create("release") {
        storeFile = file("release.keystore")
        storePassword = System.getenv("KEYSTORE_PASSWORD")
        keyAlias = "release"
        keyPassword = System.getenv("KEY_PASSWORD")
        enableV1Signing = true
        enableV2Signing = true
        enableV3Signing = true
    }
}
```

验证签名：

```bash
apksigner verify --print-certs app-release.apk
```

注意事项：

* 密钥文件和密码不要提交到仓库，使用环境变量或 CI 的 Secret 管理；推荐使用 Google Play App Signing 保管上传密钥。
* 更换签名密钥会导致无法覆盖安装，必须通过 v3 密钥轮换或换包名。
* 签名前先 `zipalign`（AGP 会自动处理），顺序错误会导致安装失败。

## 7 发布前检查清单

| 检查项 | 要求 |
| --- | --- |
| `debuggable` | release 必须为 false |
| R8 / 资源压缩 | 均已开启，mapping 已归档 |
| 签名 | 正式 keystore，`apksigner verify` 通过 |
| 版本号 | versionCode 递增，versionName 符合规范 |
| 日志 | 关闭调试日志，敏感信息脱敏 |
| 网络 | 生产域名、HTTPS、cleartext 关闭 |
| 权限 | 最小化，敏感权限有使用说明 |
| 组件暴露 | `exported` 按需设置，`PendingIntent` 使用 `FLAG_IMMUTABLE` |
| 64 位 | 包含 `arm64-v8a`，满足应用市场要求 |
| targetSdk | 满足 Google Play / 国内市场的时限要求 |
| 升级 | 覆盖安装、跨版本升级、数据迁移验证通过 |
| 兼容 | 低端机、弱网、深色模式、大字体、多语言 |
| 监控 | 崩溃、ANR、启动、核心链路埋点已接入 |

## 8 灰度发布

* 按比例（5% → 20% → 50% → 100%）和维度（机型、系统、地域、渠道、用户哈希）灰度，每档观察足够时长。
* 服务端开关：新功能用配置中心控制，出问题先关开关，不必等发版。
* 观察崩溃率、ANR 率、启动耗时、核心转化；出问题停止放量、服务端降级或发紧急修复版。
* 注意 `versionCode` 不能回退安装，回滚要靠服务端兼容旧版本；应用市场支持 staged rollout 的优先使用。

## 9 热修复注意点

热修复可以在不发版的情况下修复线上问题，但不是万能的：

* **原理与限制**：Tinker 通过 dex 差量补丁替换有问题的类，Robust 通过方法替换；不能新增四大组件，不能修改 `AndroidManifest.xml`，资源修复有较多限制。
* **基线**：补丁必须基于已发布的版本构建，版本号、签名、混淆 mapping 都要匹配。
* **安全与合规**：补丁要签名校验、加密传输；不能通过热修复动态加载代码绕过应用市场审核，Google Play 对动态代码加载有严格限制。
* **灰度与兜底**：补丁先小比例验证再全量；加载失败要能安全回退到原版本，不能导致启动崩溃。

热修复适合修紧急、局部的 bug；结构性问题、性能问题、需要新增能力的，仍然应该走正常发版流程。
