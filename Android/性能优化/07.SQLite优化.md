## 1 SQLite 与 Android

SQLite 是进程内的嵌入式关系型数据库，Android 通过 `SQLiteDatabase`、`SQLiteOpenHelper` 提供封装，Room 在其上增加编译期 SQL 校验、实体映射和协程支持。

| 特性 | 说明 |
| --- | --- |
| 存储 | 单文件，位于 `/data/data/<pkg>/databases/` |
| 事务 | 支持 ACID，默认每条语句一个事务 |
| 并发 | 多读单写；WAL 模式下读写不互斥 |
| 类型 | 动态类型，INTEGER / REAL / TEXT / BLOB / NULL |
| 适合 | 结构化数据、列表、搜索、统计 |

数据库操作的耗时主要来自：**磁盘 IO 与 fsync、SQL 解析、CursorWindow 数据拷贝、锁等待**。优化也围绕这四点展开。

## 2 事务与批量插入

### 2.1 为什么批量写要包事务

SQLite 默认把每条语句当作一个事务，提交时要做一次日志落盘（fsync）。循环插入 1000 条就是 1000 次事务提交，速度会慢一两个数量级。包在一个事务里，只有最后一次提交需要落盘。

```java
SQLiteDatabase db = helper.getWritableDatabase();
db.beginTransaction();
try {
    for (User user : users) {
        db.insert("user", null, toContentValues(user));
    }
    db.setTransactionSuccessful(); // 标记成功，否则回滚
} finally {
    db.endTransaction();
}
```

### 2.2 预编译语句与事务批量插入

`insert()` 每次都会重新解析 SQL，批量场景应复用 `SQLiteStatement`：

```java
db.beginTransaction();
SQLiteStatement stmt = db.compileStatement("INSERT INTO user(name, age) VALUES(?, ?)");
try {
    for (User user : users) {
        stmt.clearBindings();
        stmt.bindString(1, user.name);
        stmt.bindLong(2, user.age);
        stmt.executeInsert();
    }
    db.setTransactionSuccessful();
} finally {
    db.endTransaction();
    stmt.close();
}
```

### 2.3 Room 的批量插入

```kotlin
@Dao
interface UserDao {
    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertAll(users: List<User>)
}
```

Room 对集合参数的 `@Insert` 会在内部开启事务并复用语句，不需要自己再包 `beginTransaction`。

### 2.4 注意事项

* 事务尽量短，不要在事务里做网络请求、UI 操作或大量计算。
* 超大批量按 500~2000 条分批提交，避免长事务阻塞写入、撑大 WAL。
* `SQLiteDatabase` 支持嵌套事务（引用计数），但 Room 的 `@Transaction` 与手写事务不要混用；插入失败要让异常抛出（`insertOrThrow`），不要静默吞掉约束错误。

## 3 索引与执行计划

### 3.1 索引基础

索引是 B-Tree 结构，用于加速 `WHERE`、`ORDER BY`、`JOIN`，代价是**写入变慢、占用空间**。常见类型：

```sql
CREATE INDEX idx_user_name ON user(name);                 -- 单列索引
CREATE UNIQUE INDEX idx_user_email ON user(email);        -- 唯一索引
CREATE INDEX idx_order_user_time ON orders(user_id, created_at); -- 联合索引
```

联合索引遵循**最左前缀**原则：`(user_id, created_at)` 可以命中 `WHERE user_id = ?`、`WHERE user_id = ? ORDER BY created_at`，但单独按 `created_at` 查询用不上。

### 3.2 用 EXPLAIN QUERY PLAN 验证

```sql
EXPLAIN QUERY PLAN SELECT * FROM user WHERE name = 'soleil';
-- SEARCH TABLE user USING INDEX idx_user_name (name=?)

EXPLAIN QUERY PLAN SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at DESC;
-- SEARCH TABLE orders USING INDEX idx_order_user_time (user_id=?)
```

| 输出关键字 | 含义 |
| --- | --- |
| `SCAN TABLE` | 全表扫描，大表上要警惕 |
| `SEARCH ... USING INDEX` | 命中索引 |
| `USING COVERING INDEX` | 索引覆盖，无需回表 |
| `USE TEMP B-TREE FOR ORDER BY` | 需要额外排序，可考虑调整索引 |

### 3.3 索引失效的常见场景

* 对索引列使用函数或表达式（`WHERE strftime('%Y', created_at) = '2024'`），或发生隐式类型转换（`phone` 是 TEXT 却写成 `WHERE phone = 13800000000`）。
* 前导模糊匹配：`LIKE '%abc'`；`LIKE 'abc%'` 仍可走索引。
* `OR` 连接的列没有全部命中索引，或联合索引未遵循最左前缀。
* `!=`、`NOT IN`、`IS NULL` 等选择性差的条件，优化器可能放弃索引；统计信息过期时执行 `ANALYZE` 更新。

索引不是越多越好：每个索引都会增加插入、更新、删除的成本，只为真正高频且选择性的查询建索引。

## 4 WAL 模式

### 4.1 原理

传统 journal 模式下，写操作会加锁并写回滚日志，读写互斥。WAL（Write-Ahead Logging）把修改**追加到 `-wal` 文件**，读操作同时读主库和 WAL，因此**读写不互相阻塞**，只有写与写之间串行。

* 需要额外的 `-shm` 共享内存文件保存索引。
* 不支持网络文件系统，只读数据库也无法启用。
* WAL 文件会周期性 checkpoint 回主库。

### 4.2 开启方式

```java
SQLiteDatabase db = helper.getWritableDatabase();
boolean ok = db.enableWriteAheadLogging(); // API 16+，返回是否成功
```

```kotlin
Room.databaseBuilder(context, AppDatabase::class.java, "app.db")
    .setJournalMode(RoomDatabase.JournalMode.WRITE_AHEAD_LOGGING)
    .build()
```

Room 默认使用 `JournalMode.AUTOMATIC`，在大多数设备上会自动启用 WAL。

### 4.3 注意事项

* 写事务仍然串行，不要以为开了 WAL 就能并发写；长事务会阻止 checkpoint，导致 WAL 文件持续增大。
* 可以通过 `PRAGMA wal_checkpoint(TRUNCATE)` 主动收缩，但不要频繁调用。
* 多进程同时访问同一数据库需要谨慎，WAL 依赖共享内存，建议把数据库访问收敛到单进程。

## 5 Cursor 使用与关闭

Cursor 持有 `CursorWindow`（默认约 2MB），不关闭会泄漏内存和文件句柄，Kotlin 用 `use` 可以自动关闭：

```kotlin
db.query("user", null, null, null, null, null, null).use { cursor ->
    val nameIndex = cursor.getColumnIndexOrThrow("name")
    while (cursor.moveToNext()) {
        val name = cursor.getString(nameIndex)
    }
}
```

使用要点：

* `getColumnIndex` / `getColumnIndexOrThrow` 只调用一次，不要放在循环里。
* 只 `SELECT` 需要的列，避免把大 BLOB、长文本装进 CursorWindow。
* 列索引只在当前 Cursor 内有效，换一条查询要重新获取；大结果集分页读取，不要在主线程一次遍历几万行。
* `SQLiteDatabase` 由 `SQLiteOpenHelper` 管理，不需要手动关闭；Cursor 必须关闭。

## 6 分页与大数据量处理

### 6.1 OFFSET 越深越慢

`LIMIT 20 OFFSET 100000` 需要扫描并丢弃前 10 万行，页码越大越慢，还可能出现数据重复或遗漏。

### 6.2 键集分页（keyset pagination）

用上一页最后一条记录的排序键作为游标，复杂度稳定：

```sql
SELECT * FROM orders
WHERE user_id = ? AND id < ?
ORDER BY id DESC
LIMIT 20;
```

要求排序键稳定且唯一（`id`、`created_at + id`），否则会漏数据。Room 中配合 Paging 3 使用时，优先让 `LIMIT` 与游标条件走索引。

### 6.3 大数据量处理

* 大批量删除、更新分批执行，每批 500~2000 条。
* 删除大量数据后执行 `VACUUM` 回收空间（需要约 2 倍数据库大小的临时空间），或使用 `PRAGMA auto_vacuum=INCREMENTAL` + `PRAGMA incremental_vacuum`。
* 定期 `ANALYZE`，让优化器拿到准确的统计信息。
* 大 BLOB 放文件系统，数据库只存路径；用 `PRAGMA page_count`、`page_size` 估算数据库大小并做监控。

## 7 Room 常用优化

### 7.1 表结构与查询

```kotlin
@Entity(
    tableName = "user",
    indices = [Index(value = ["email"], unique = true), Index("age")]
)
data class User(
    @PrimaryKey val id: Long,
    val email: String,
    val age: Int
)
```

* 只为高频查询建索引，唯一约束用 `unique = true`；查询只取需要的列（projection），避免 `SELECT *`。
* 多条相关查询用 `@Transaction` 保证一致性；`@Relation` 注意 N+1 查询，数据量大时改用手写 JOIN。
* 列表查询返回 `Flow<List<T>>`，Room 在表变化时自动推送；写操作使用 `suspend`。
* `@TypeConverters` 只做简单类型转换，复杂结构应拆表。

### 7.2 运行期注意

* 不要开启 `allowMainThreadQueries()`，查询放 IO 线程；`exportSchema = true` 并提交 schema 文件，方便迁移测试与 Code Review。
* 多进程不要同时使用同一个 Room 数据库（Room 没有跨进程失效通知）；数据库加密可用 SQLCipher（`net.zetetic:sqlcipher-android`），通过 `openHelperFactory` 接入，密钥存 Keystore，加密会带来约 5%~15% 的性能损耗。

## 8 数据库升级与迁移

### 8.1 手写 Migration

```kotlin
val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE user ADD COLUMN nickname TEXT")
    }
}

Room.databaseBuilder(context, AppDatabase::class.java, "app.db")
    .addMigrations(MIGRATION_1_2)
    .build()
```

### 8.2 自动迁移

```kotlin
@Database(
    entities = [User::class],
    version = 2,
    autoMigrations = [AutoMigration(from = 1, to = 2)]
)
abstract class AppDatabase : RoomDatabase()
```

`AutoMigration` 只适合加列、加表等简单变更；改名、拆表、数据搬迁仍然要手写 `Migration`，并用 `@RenameColumn`、`@DeleteColumn` 等注解辅助。

### 8.3 迁移的坑

* `fallbackToDestructiveMigration()` 会直接清空数据库，只能用于缓存库或开发期；迁移中不要调用 Room DAO（此时数据库还没准备好），用 `execSQL`。
* 迁移必须幂等、可重入，考虑用户跨多个版本升级（1→2→3），并用 `MigrationTestHelper` 为每个版本写测试。
* 已发布的 schema 不要修改，只能追加新版本与迁移；迁移失败会抛 `IllegalStateException`，要有兜底（备份、重建、上报），不要直接让应用崩溃。
