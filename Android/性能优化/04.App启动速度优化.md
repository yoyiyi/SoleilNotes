## 1 启动类型

| 类型 | 进程 | Application | Activity | 耗时 |
| --- | --- | --- | --- | --- |
| 冷启动 | 新建 | 重新创建 | 重新创建 | 最长 |
| 温启动 | 已存在 | 不重建 | 重新创建 | 中等 |
| 热启动 | 已存在 | 不重建 | 已存在，仅回前台 | 最短 |

冷启动时进程不存在，系统要从 Zygote fork 新进程，依次创建 Application 和目标 Activity，直到首帧绘制完成，是启动优化的主要目标。温启动时进程还在，但 Activity 已被销毁，需要重建 Activity 并恢复状态。热启动只是把后台的 Activity 带回前台，通常只走 `onRestart`、`onStart`、`onResume`。

## 2 启动流程与耗时点

### 2.1 系统侧流程

1. Launcher 收到点击事件，调用 `startActivity()`。
2. 通过 Binder 进入 system_server 的 ATMS（Android 10 之前是 AMS）。
3. ATMS 检查进程是否存在，不存在则请求 Zygote fork 新进程。
4. 新进程执行 `ActivityThread.main()`，向 ATMS 注册 `ApplicationThread`。
5. ATMS 通知应用进程执行 `bindApplication`。
6. 应用创建 Application，执行 `attachBaseContext()`、`onCreate()`。
7. 创建并启动目标 Activity，执行 `onCreate()`、`onStart()`、`onResume()`。
8. `ViewRootImpl` 开始 measure/layout/draw，提交首帧。
9. 首帧显示后，系统输出 Displayed 日志。

### 2.2 应用侧耗时点

* `attachBaseContext()`：MultiDex、资源加载。
* `ContentProvider.onCreate()`：每个 Provider 都在 `Application.onCreate()` 之前创建，第三方 SDK 常用这种方式自动初始化。
* `Application.onCreate()`：主线程 IO、设备信息、日志、统计、大量类加载与反射、锁竞争。
* Activity 创建：`setContentView()`、布局 inflate、数据绑定。
* 首帧渲染：measure/layout/draw、图片解码、字体加载。

其中 ContentProvider 和 Application 的初始化最容易被第三方 SDK 拖慢，因为它们在 Activity 创建之前同步执行。

### 2.3 首帧与 reportFullyDrawn

系统默认以首帧绘制完成作为启动结束。如果首帧只显示骨架屏，真正的内容还在异步加载，可以调用 `reportFullyDrawn()` 告诉系统“内容已经完整展示”，便于统计用户真正可用的时间。

## 3 启动耗时统计

### 3.1 adb am start -W

```bash
adb shell am force-stop com.example.app
adb shell am start -W -n com.example.app/.MainActivity
```

```text
Status: ok
LaunchState: COLD
Activity: com.example.app/.MainActivity
ThisTime: 856
TotalTime: 856
WaitTime: 912
```

`ThisTime` 是最后一个 Activity 的启动耗时，`TotalTime` 是本次启动所有 Activity 的总耗时，`WaitTime` 是从 `startActivity` 到系统返回的总耗时。多次执行取中位数，并区分冷、温、热启动。

### 3.2 Displayed 日志

```bash
adb logcat -s ActivityTaskManager ActivityManager | grep -i displayed
```

```text
ActivityTaskManager: Displayed com.example.app/.MainActivity: +856ms
```

Android 10 之前 tag 是 `ActivityManager`，之后是 `ActivityTaskManager`。这条日志统计从 `startActivity` 到首帧绘制完成的时间，适合快速验证。代码中可以用 `Process.getStartUptimeMillis()`（API 24+）配合 `SystemClock.uptimeMillis()` 打点，在 `onCreate()`、`onResume()` 和 `OnPreDrawListener` 中拆分各阶段耗时。

## 4 优化手段

### 4.1 启动器与任务编排

启动任务之间存在依赖，例如“上报模块”依赖“设备信息模块”。可以用有向无环图（DAG）描述依赖，再按拓扑排序分组执行：

```java
public interface StartupTask {
    String name();
    List<String> dependencies();
    void run();
}
```

启动器把无依赖的任务提交到线程池并行执行，依赖任务通过 `CompletableFuture` 等待前置任务完成；必须在首帧前完成的任务才同步执行，其余延迟或异步。并发数不宜过高，低端机上线程过多反而更慢。

### 4.2 异步初始化

把不阻塞首帧的初始化放到子线程：

```java
ExecutorService initExecutor = Executors.newFixedThreadPool(2);
initExecutor.execute(() -> {
    DeviceInfo.init(context);
    Analytics.init(context);
});
```

注意区分“必须在首帧前完成”和“可以稍后完成”的任务，控制线程数量，确认 SDK 的 `init()` 是否线程安全，并做好失败降级。

### 4.3 懒加载与按需初始化

* 把只在特定页面使用的 SDK 移到对应页面首次进入时初始化。
* 使用单例 + 双重检查锁延迟创建对象。
* 用 `IdleHandler` 在消息队列空闲时执行非紧急任务：

```java
Looper.myQueue().addIdleHandler(() -> {
    initNonCriticalModules();
    return false; // 只执行一次
});
```

* 避免在 `Application.onCreate()` 中做网络请求、数据库全量查询和大量反射。

### 4.4 启动窗口与白屏

启动到首帧之间，系统先显示启动窗口，其背景由主题的 `windowBackground` 决定。如果主题背景是白色而页面是深色，就会看到白屏闪烁。

* 把 `windowBackground` 设置为与首屏一致的背景色或启动图。
* 用 `layer-list` 实现居中的 Logo，避免单独启动页 Activity。
* Android 12 及以上使用 SplashScreen API（引入 `androidx.core:core-splashscreen`）：

```java
SplashScreen splashScreen = SplashScreen.installSplashScreen(this);
splashScreen.setKeepOnScreenCondition(() -> !viewModel.isDataReady());
super.onCreate(savedInstanceState);
setContentView(R.layout.activity_main);
```

```xml
<style name="Theme.App.Starting" parent="Theme.SplashScreen">
    <item name="windowSplashScreenBackground">@color/splash_bg</item>
    <item name="windowSplashScreenAnimatedIcon">@drawable/ic_logo</item>
    <item name="postSplashScreenTheme">@style/Theme.App</item>
</style>
```

不要使用透明主题来“消除”启动窗口，这会让用户看到桌面或上一个应用，产生点击无响应的感觉。

### 4.5 Dex 与编译优化

* 开启 R8 代码压缩和资源压缩，减少 dex 数量和类加载开销。
* `minSdk >= 21` 时使用原生 Multidex，避免 `MultiDex.install()` 的同步耗时。
* 使用 Baseline Profile 让热点代码提前 AOT 编译（见第 5 节）。
* 对已安装应用手动触发编译，验证 dexopt 的影响：

```bash
adb shell cmd package compile -m speed -f com.example.app
```

### 4.6 类预加载

首帧前集中加载大量类会造成耗时，可以在后台线程用 `Class.forName()` 提前加载。预加载要适度：加载过多会占用内存和 CPU，也可能与主线程的类加载产生锁竞争。只预加载确定会用到、且初始化成本高的类。

### 4.7 布局与首帧优化

* 减少布局层级，使用 ConstraintLayout、`merge`、`ViewStub`。
* 首帧只加载首屏可见内容，列表分页加载。
* 图片按显示尺寸解码，避免首帧解码大图。
* 避免在 `onCreate()` 中执行数据库查询和网络请求。
* 减少 ContentProvider 数量，移除不需要的第三方 Provider。

## 5 基线 Profile

Baseline Profile 记录应用启动和常用场景下的热点方法，安装时由 ART 提前编译为机器码，减少解释执行和 JIT 编译，从而缩短启动时间并降低卡顿。Android 7.0（API 24）及以上可以通过 `profileinstaller` 安装。

使用 Macrobenchmark 生成：

```kotlin
@RunWith(AndroidJUnit4::class)
class BaselineProfileGenerator {
    @get:Rule
    val rule = BaselineProfileRule()

    @Test
    fun generate() = rule.collect("com.example.app") {
        pressHome()
        startActivityAndWait()
    }
}
```

在 AGP 8.2 及以上执行 `./gradlew :app:generateBaselineProfile`，生成的 `baseline-prof.txt` 会打包为 `assets/dexopt/baseline.prof`。应用侧添加依赖即可，`profileinstaller` 会在启动时安装：

```groovy
implementation "androidx.profileinstaller:profileinstaller:1.3.1"
```

Profile 需要一次安装或后台编译才能生效，验证时要多跑几轮并对比冷启动耗时。

## 6 Jetpack App Startup

很多库通过 ContentProvider 自动初始化，每个 Provider 都会增加启动开销。引入 `androidx.startup:startup-runtime` 后，App Startup 会提供一个统一的 `InitializationProvider`，把所有 `Initializer` 集中初始化，并支持依赖排序。

```java
public class AnalyticsInitializer implements Initializer<Analytics> {
    @Override
    public Analytics create(Context context) {
        Analytics analytics = Analytics.getInstance();
        analytics.init(context);
        return analytics;
    }

    @Override
    public List<Class<? extends Initializer<?>>> dependencies() {
        return Collections.emptyList();
    }
}
```

在 Manifest 中注册：

```xml
<provider
    android:name="androidx.startup.InitializationProvider"
    android:authorities="${applicationId}.androidx-startup"
    android:exported="false"
    tools:node="merge">
    <meta-data
        android:name="com.example.app.AnalyticsInitializer"
        android:value="androidx.startup" />
</provider>
```

不需要在启动时初始化的组件，可以用 `tools:node="remove"` 移除自动注册，再手动调用：

```java
AppInitializer.getInstance(context)
        .initializeComponent(AnalyticsInitializer.class);
```

App Startup 本身仍是 ContentProvider，所有初始化都在 `Application.onCreate()` 之前完成。如果对启动时间要求极高，可以移除该 Provider，完全改为手动初始化。

## 7 监控与验收

* 指标：冷启动 P50/P90/P99、温启动耗时、首帧耗时、`reportFullyDrawn` 耗时。
* 分维度：设备型号、Android 版本、CPU 架构、低端机、首次安装。
* 对比：同一设备、同一版本、同一场景，多次采样取中位数。
* 线上：启动埋点上报，同时观察崩溃率和 ANR 率是否上升。

## 8 总结

* 冷启动包含进程创建、Application 初始化、Activity 创建和首帧渲染，是优化重点。
* 用 `am start -W`、Displayed 日志、代码打点和 Macrobenchmark 量化启动耗时。
* 优化方向包括任务编排、异步初始化、懒加载、启动窗口、Dex 优化和类预加载。
* Baseline Profile 和 Jetpack App Startup 成本较低、收益明显。
* 启动优化要区分首帧和内容可用，避免为了数字好看牺牲真实体验。
