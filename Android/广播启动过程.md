## 1 简介

广播的注册分为静态注册和动态注册，主要分析动态注册，可以从三个方面来分析；

* 广播的注册
* 广播的发送
* 广播的处理

> 2025 更新：上面三条主线没变，但两个前提变了——Android 8.0（API 26）起静态注册收不到大部分隐式广播；Android 14（targetSdk 34）起动态注册必须显式声明 `RECEIVER_EXPORTED`/`RECEIVER_NOT_EXPORTED`。本文以动态注册为例的分析仍然成立，细节见第 3 节。

registerReceiver() 有多个重载函数，最终调用到以下函数。

```java
private Intent registerReceiverInternal(BroadcastReceiver receiver, int userId, IntentFilter filter, String broadcastPermission, Handler scheduler, Context context) {
    IIntentReceiver rd = null;
    if (receiver != null) {
        if (mPackageInfo != null && context != null) {
            if (scheduler == null) {
                //将 scheduler 赋值为 主线程的 Handler

            //代码一：获取 IIntentReceiver对象 mPackageInfo -> LoasedApk 类型

                receiver, context, scheduler,

            if (scheduler == null) {
                scheduler = mMainThread.getHandler();
            }
            rd = new LoadedApk.ReceiverDispatcher(
                  receiver, context, scheduler, null, true).getIIntentReceiver();
        }
    }
    try {
        //代码二：调用 ActivityManagerProxy(AMP) 的 registerReceiver
        return ActivityManagerNative.getDefault().registerReceiver(
                mMainThread.getApplicationThread(), mBasePackageName,
                rd, filter, broadcastPermission, userId);

        return null;
    }
}
```

## 3 Android 12—16 的变化与面试追问

> 本节覆盖 **Android 8.0（API 26）—Android 16（API 36）**。原文分析的是 Android 9 前后的 AOSP，下面把之后改"语义"的部分补齐；只是类名/实现重构的，会标注"以 AOSP 为准"。

### 3.1 Android 8.0：隐式广播限制与豁免清单

Android 8.0（API 26）起，**manifest 静态注册**的 receiver 收不到大部分隐式广播；动态注册不受影响（这也是原文只分析动态注册依然成立的原因）。

官方"Implicit broadcast exceptions"清单（记忆版）：

* `ACTION_BOOT_COMPLETED`、`ACTION_LOCKED_BOOT_COMPLETED`
* `ACTION_USER_INITIALIZE`、`ACTION_TIMEZONE_CHANGED`、`ACTION_TIME_CHANGED`、`ACTION_LOCALE_CHANGED`
* `ACTION_MY_PACKAGE_REPLACED`
* `ACTION_PACKAGE_DATA_CLEARED`（只发给被清数据的应用自己）、`ACTION_PACKAGE_FULLY_REMOVED`
* `ACTION_NEW_OUTGOING_CALL`、`ACTION_DEVICE_OWNER_CHANGED`、`ACTION_EVENT_REMINDER`
* 媒体挂载类 `ACTION_MEDIA_MOUNTED`/`UNMOUNTED`/`EJECT`（只发给拥有该媒体的应用）
* 短信/MMS 类（`SMS_RECEIVED`、`WAP_PUSH_RECEIVED`）
* 完整清单以官方 "Implicit broadcast exceptions" 文档为准

发送方还可以用 `Intent.FLAG_RECEIVER_INCLUDE_BACKGROUND` 显式放行（需要权限）、`FLAG_RECEIVER_EXCLUDE_BACKGROUND` 反向排除。

结论：静态注册只留给"应用没启动也要收到"的系统事件，且必须落在豁免清单里；业务广播一律动态注册，或直接换成 `Flow`/`LiveData`。

### 3.2 Android 13/14：动态注册必须声明导出行为

* Android 13（API 33）废弃两参数 `registerReceiver()`；
* targetSdk 34（Android 14）起，动态注册**非系统广播**必须显式指定：
  * `Context.RECEIVER_EXPORTED`：其他应用可以给你发；
  * `Context.RECEIVER_NOT_EXPORTED`：只接收本应用/系统广播；
* 不指定会抛 `SecurityException`（"One of RECEIVER_EXPORTED or RECEIVER_NOT_EXPORTED should be specified..."）；只注册系统保护广播时可以不传，但建议统一传；
* 兼容写法：`ContextCompat.registerReceiver(context, receiver, filter, ContextCompat.RECEIVER_NOT_EXPORTED)`；
* manifest 静态注册：targetSdk 31（Android 12）起带 `<intent-filter>` 的组件必须显式写 `android:exported`，否则安装失败；
* `RECEIVER_NOT_EXPORTED` 才是默认该选的：导出意味着输入不可信，要校验 action、包名、`getSendingUid()`，或用 `android:permission`/`sendBroadcast(intent, permission)` 收口。

### 3.3 Android 4.4—16：BroadcastQueue 的前台/后台队列（不是 10 才拆的）

* AMS 持有两条 `BroadcastQueue`：`mFgBroadcastQueue`/`mBgBroadcastQueue`，这套前台/后台拆分早在 Android 4.4（KitKat）的 AMS 里就已存在，比 Android 10 早得多；由 `Intent.FLAG_RECEIVER_FOREGROUND` 经 `broadcastQueueForIntent()` 选择；每条队列内部再分并行列表 `mParallelBroadcasts` 和串行列表 `mOrderedBroadcasts`；
* 前台队列超时约 10s、后台约 60s（`BROADCAST_FG_TIMEOUT`/`BROADCAST_BG_TIMEOUT`），超时打印 "Timeout of broadcast ..." 并 ANR；
* 两条队列各自串行：同一条队列里前一个广播卡住，后面的广播（包括同应用的）全部排队——这是"广播导致 ANR"最常见的原因；
* Android 14 起 AOSP 对 `BroadcastQueue` 做过实现层重构，类结构会变，但"前台/后台 + 超时 + 有序语义"不变。

### 3.4 有序广播与 goAsync

有序广播（`sendOrderedBroadcast`）：

* 按 `android:priority`/`IntentFilter#setPriority` 从高到低**串行**投递；
* 接收方可以 `setResultCode()`/`setResultData()`/`setResultExtras()` 把结果传给下一个，也可以 `abortBroadcast()` 终止；
* `resultReceiver` 拿到最终结果，`Handler` 版本可以指定回调线程；
* 代价是串行 + 全局锁，跨应用"必须终止后续接收"才用，普通业务别用。

`goAsync()`：

* 在 `onReceive` 里调用，返回 `PendingResult`，让系统认为这次分发还没结束，可以丢到子线程干活，干完必须 `pendingResult.finish()`；
* `onReceive` 本身仍在主线程，`goAsync` 只是把"结束信号"延后，**没有**给你无限时间：前台约 10s、后台约 60s 内必须 `finish()`，否则 ANR；
* `goAsync` 不会提升进程优先级，进程该被杀还是会被杀；
* 超过 10s 的活交给 `WorkManager`/`JobScheduler`（可 `setExpedited`/`setForeground`），不要在 receiver 里硬扛。

### 3.5 广播 vs WorkManager vs Messenger

| 维度 | BroadcastReceiver | WorkManager | Messenger |
| --- | --- | --- | --- |
| 用途 | 系统事件、跨应用一次性通知 | 可延迟、需保证执行的后台任务 | 跨进程双向消息（串行队列） |
| 生命周期 | `onReceive` 主线程约 10s | 由 WorkManager 调度，进程死了也会重试 | 绑定服务的生命周期 |
| 跨进程 | 是（Binder 广播） | 否（同应用） | 是（Binder + Handler） |
| 可靠性 | 不保证（注册了才收） | 保证（约束/重试/持久化） | 连接断开即失效 |
| 典型坑 | 隐式限制、导出、ANR | 约束不满足一直等 | 串行队列，别塞大对象 |

选型结论：

* 进程内事件：`SharedFlow`/`LiveData` > `LocalBroadcastManager`（2021 年已废弃）；
* "应用没启动也要收到"：只有静态注册的系统广播，且必须在豁免清单里；
* "顺序 + 可回传结果"：`Messenger` 或 `bindService` + AIDL 比有序广播更可控；
* "一定要执行完"：`WorkManager`，广播只负责"通知一下"。

### 3.6 Android 15/16 的边际变化

* Android 15（API 35）：`BOOT_COMPLETED` receiver 不能再启动 `dataSync`/`camera`/`mediaPlayback`/`phoneCall`/`mediaProjection`/`microphone` 类型的 FGS——广播限制和前台服务限制在这里交汇，是近两年的高频面试点；
* Android 16（API 36）：广播模型没有结构性变化，仍是"静态注册收紧 + 导出显式化 + 后台限制"的延续，新增/调整的保护广播以官方文档为准。

### 3.7 面试追问（6—8 个）

1. **Android 8.0 为什么限制隐式广播？豁免清单怎么记？** 省电（避免应用被隐式广播频繁拉活）；记"开机、时区/时间/语言、包替换/卸载、媒体挂载、短信、设备管理"几类，其余按文档查。
2. **静态注册和动态注册在 8.0 之后分别受什么限制？** 静态：隐式广播限制 + targetSdk 31 的 `android:exported` 必填；动态：targetSdk 34 起必须声明 `RECEIVER_EXPORTED`/`NOT_EXPORTED`。
3. **两个导出 flag 怎么选？** 只收自己/系统广播选 `NOT_EXPORTED`；确实要给第三方发才 `EXPORTED`，并配权限校验。
4. **前台队列/后台队列怎么分？广播 ANR 怎么定位？** `FLAG_RECEIVER_FOREGROUND` 决定；看 logcat "Timeout of broadcast" 与 `dumpsys activity broadcasts` 里的队列和 `BroadcastRecord` 耗时。
5. **有序广播的 `abortBroadcast`/`resultReceiver` 怎么用？为什么现在不推荐？** 串行、持锁、易被前一个 receiver 拖死；能换 `Messenger`/`WorkManager` 就换。
6. **`goAsync` 能解决 ANR 吗？不调 `finish()` 会怎样？** 只争取到异步时间，不延长超时；不 `finish()` 会 ANR，还会让后续广播排队。
7. **广播、`WorkManager`、`Messenger` 怎么选？** 一次性通知/系统事件用广播，必须执行完用 `WorkManager`，双向 RPC 用 `Messenger`/AIDL。
8. **Android 15 上 `BOOT_COMPLETED` 启动前台服务有什么坑？** 那 6 类 FGS 在开机广播里直接被拒（`ForegroundServiceStartNotAllowedException`），要改成 `WorkManager` 或延后到用户打开应用后再起。
