## 1 简介

应用程序进程启动过程分为三步骤：

* AMS 通过 socket 向 zygote 发送创建应用程序进程请求 
* zygote 接收请求并创建应用程序进程
* 应用进程创建后会启动 **Binder 线程池**以及**开启消息循环机制**

## 3 Android 12—16 的变化与面试追问

> 2025 更新：前文基于 Android 9/10 的 Zygote/ActivityThread 源码。Android 10 起客户端拆出 `ZygoteProcess`、服务端拆出 `ZygoteServer`，部分设备还启用 USAP 池；本节按 Android 12—16（API 31—36）补现代链路，具体方法名以对应 AOSP 分支为准。

### 3.1 现代链路：从 Process.start 到 ActivityThread.main

可以把一次冷启动拆成“客户端发命令、Zygote 服务端 fork、子进程特化、跑 ActivityThread”四段：

1. system_server 侧：AMS 的 `startProcessLocked()` 组装 uid/gid/gids、seInfo、ABI、entryPoint（默认 `android.app.ActivityThread`）等参数，调用 `Process.start()`。
2. 客户端：`Process.start()` 转给 `ZygoteProcess.start()`，再走 `startViaZygote()`；`openZygoteSocketIfNeeded()` 根据 ABI 选择主/次 Zygote 的 `ZygoteState`，把参数通过 socket 发过去。
3. 服务端：Zygote 的 `ZygoteServer.runSelectLoop()` 收到连接，交给 `ZygoteConnection` 的 `runOnce()`/`processCommand()` 解析成 `ZygoteArguments`；随后调用 `Zygote.forkAndSpecialize()`（或 USAP 池的 `specializeAppProcess()`）创建/特化子进程。
4. 子进程：`handleChildProc()` → `RuntimeInit.zygoteInit()` → `nativeZygoteInit()` 启动 Binder 线程池 → `applicationInit()` 反射调用 `ActivityThread.main()`；`ActivityThread.main()` 里 `Looper.prepareMainLooper()`、`attach(false)`、`Looper.loop()`。

几个关键角色不要混淆：

* `ZygoteProcess` 是 system_server 侧的客户端代理，负责 socket 连接、ABI 匹配和发参数；`ZygoteServer` 是 Zygote 侧的服务端循环；`ZygoteConnection` 处理单次连接；`ZygoteState` 保存已连接的 socket 和 ABI 信息。
* `Zygote.forkAndSpecialize()` 在 native 层完成 fork 和 uid/gid/gids、capabilities、seccomp 等特化；子进程只保留一个线程，随后才启动 Binder 线程池，避免 fork 出带锁的多线程状态。
* `specializeAppProcess()` 主要服务于 USAP（Unspecialized App Process）池：Zygote 预先 fork 出“未特化”的进程，收到请求后再设置 uid/gid 等，减少 fork 的延迟。USAP 是否启用取决于版本、设备和配置，不要把它当成所有 Android 的必经路径。
* `RuntimeInit.zygoteInit()` 的签名在不同版本有变化（可能多出 disabled compat changes 等参数），但“先 `nativeZygoteInit()` 起 Binder 池，再 `applicationInit()` 进 ActivityThread”这个顺序是稳定的。

`ActivityThread.main()` 并不是“应用自己启动”的：它是被 Zygote 子进程通过反射调用的入口。`attach(false)` 会通过 Binder 调用 AMS 的 `attachApplication()`，AMS 再回调 `ApplicationThread.bindApplication()`，最终在 `handleBindApplication()` 里创建 Application、安装 ContentProvider，然后才进入 `Looper.loop()` 处理后续的 Activity/Service 消息。

再补两个链路细节：Zygote 启动时的 `preload()` 会预加载常用类、资源、共享库等，fork 后子进程 COW 共享；`openZygoteSocketIfNeeded()` 先连主 Zygote，ABI 不匹配再尝试 `zygote_secondary`，所以 32/64 位混合设备上可能有两个 Zygote。ABI 选择、socket 连接失败和 fork 失败都会以 `ZygoteStartFailedEx` 等形式回到 AMS，最终表现为进程启动失败。

### 3.2 Application 与 ContentProvider 的初始化顺序

`ActivityThread.handleBindApplication()` 的顺序可以简化为：

1. `LoadedApk.makeApplication()`：通过 `Instrumentation.newApplication()` 创建 Application，调用 `Application.attach()`/`attachBaseContext()`；此时 `onCreate()` 还没执行。
2. `installContentProviders()`：对 manifest 中声明的每个 Provider 执行 `ContentProvider.attachInfo()`/`onCreate()`；Provider 的 `initOrder` 会影响顺序。
3. `Instrumentation.callApplicationOnCreate()`：最后才回调 `Application.onCreate()`。

所以“ContentProvider 比 Application.onCreate 先初始化”不是玄学，而是系统刻意保证的：其他组件可能在 Application 还没完全起来时就需要访问 Provider，系统必须先把它安装好。代价是每个 Provider 的 `onCreate()` 都跑在主线程，任何磁盘、网络、数据库初始化都会直接拖慢冷启动。

治理启动时的 Provider 可以从这几步入手：

* 数一数 manifest 里有多少个 `ContentProvider`（包括第三方 SDK 自动 merge 进来的），把非必要的初始化改成懒加载。
* 用 `android:initOrder` 明确依赖顺序，避免 Provider 之间隐式依赖导致“谁先跑”不确定。
* 用 AndroidX App Startup 把多个 `Initializer` 收敛到一个 `InitializationProvider`，通过 `dependencies()` 建拓扑顺序；它减少的是 Provider 数量和顺序混乱，不是把初始化移出主线程。
* 对确实很重的 SDK，用 `tools:node="remove"` 去掉它的自动 Provider，改由业务在合适的时机显式初始化；同时确认不会破坏 SDK 的契约。

```kotlin
class AnalyticsInitializer : Initializer<Analytics> {
    override fun create(context: Context): Analytics {
        return Analytics.init(context) // 仍然在主线程，别做重活
    }

    override fun dependencies(): List<Class<out Initializer<*>>> = emptyList()
}
```

```xml
<provider
    android:name="androidx.startup.InitializationProvider"
    android:authorities="${applicationId}.androidx-startup"

    <meta-data

```

App Startup 的 `InitializationProvider` 本身也是一个 ContentProvider，所以它仍然发生在 `Application.onCreate()` 之前；如果 `create()` 里做耗时操作，启动一样会慢。真正的优化是“减少要做的事 + 延迟到需要时 + 用 Baseline Profile 让必要代码跑得更快”。

### 3.3 App Startup、Baseline Profile 与启动优化

App Startup 解决“初始化代码分散、顺序不可控、Provider 太多”；Baseline Profile 解决“必要代码在首次安装后没有及时 AOT 编译，解释执行/低优化执行慢”。两者不是替代关系。

* Baseline Profile 通常是 `src/main/baseline-prof.txt`（或通过 `BaselineProfileRule` 生成），由 `ProfileInstaller` 在安装后/后台交给 ART 编译；它让冷启动路径上的类和方法以更优的编译模式运行，减少 JIT/解释开销。
* Baseline Profile 不会减少 Zygote fork、Provider 数量或 Binder 调用次数；它优化的是“同样跑这些代码”的执行效率。启动链路本身的重构（懒加载、并行、去掉无用 Provider）仍然要做。
* Android 12 起系统 SplashScreen 默认存在；`installSplashScreen()` + `setKeepOnScreenCondition()` 可以把启动窗口保留到首帧准备好，改善“感知启动”，但不能伪造真正的冷启动耗时。
* 线上度量不要只看 `onCreate` 到 `onResume`：用 `reportFullyDrawn()`、Macrobenchmark、`ApplicationStartInfo`（Android 15/API 35 起可用）区分进程创建、bindApplication、首帧和完全绘制。
* 启动优化要区分 cold/warm/hot start：cold start 包含 fork + Application + Provider + Activity 创建；warm/hot 主要省掉进程创建，优化重点不同。

### 3.4 进程优先级、adj 与冻结（现代版）

现代 AMS 用 `OomAdjuster` 根据进程承载的组件和状态计算 adj，`ProcessList` 保存常量并写入 `/proc/<pid>/oom_score_adj`；`ActivityManager.RunningAppProcessInfo.importance` 是应用可读的映射，不是内核里的原始值。

* `oom_adj` 是旧接口，现代内核用 `oom_score_adj`（约 -1000～1000）；AMS 口头仍说 adj，但最终影响内核的是 score。
* 内存压力下主要由用户态 `lmkd` 选择牺牲者（Android 9 起替代内核 lowmemorykiller，后续版本利用 PSI 等信号）；AMS 负责提供优先级和 kill 依据，厂商可能改写策略。
* Android 11 起 AOSP 引入 `CachedAppOptimizer`/进程冻结：缓存进程先 freeze、停止调度，能不杀就不杀；再次需要时解冻。是否默认启用取决于版本和厂商配置；冻结能保留状态，但被冻结进程的 Binder 事务可能延后/超时，系统会按需解冻。
* FGS、可见 Activity、前台绑定等会提升 adj；普通缓存进程落在 `CACHED_APP_MIN_ADJ`～`CACHED_APP_MAX_ADJ` 区间。不要把具体数值当稳定 API，答“谁计算、按什么状态计算”更重要。
* 应用无法直接写自己的 adj；能做的是 FGS、绑定关系、`WakeLock`、`onTrimMemory()` 等。`ApplicationExitInfo`（API 30+）可拿到 `REASON_LOW_MEMORY`、`REASON_ANR` 等退出原因，是线上排查入口。

### 3.5 面试追问

**Q1：Zygote 为什么用 fork 而不是 exec？**

Zygote 启动时已经预加载了常用类、资源和 native 库，fork 后子进程通过 COW 共享这些内存，不需要重新加载；exec 会丢掉预加载成果，冷启动会慢很多。fork 还要求 Zygote 保持单线程，避免复制出带锁的多线程状态，所以 Binder 线程池要等 fork 之后再启动。

**Q2：`ZygoteProcess`、`ZygoteServer`、`ZygoteConnection` 分别做什么？**

`ZygoteProcess` 是 system_server 侧的客户端，负责连 socket、匹配 ABI、发参数；`ZygoteServer` 是 Zygote 侧的事件循环，监听 socket 并接受连接；`ZygoteConnection` 处理单次连接，解析 `ZygoteArguments` 并触发 fork/特化。三者是“客户端代理—服务端循环—单连接处理”的关系。

**Q3：`specializeAppProcess()` 是什么？**

它是 USAP 池路径上的特化步骤：Zygote 先 fork 出未特化进程，收到具体请求后再设置 uid/gid/gids、seccomp、capabilities 等，减少每次 fork 的开销。不是所有设备都启用 USAP，传统 `forkAndSpecialize()` 仍是主线。

**Q4：为什么 ContentProvider 比 Application.onCreate 先执行？**

因为 `handleBindApplication()` 先 `makeApplication()`（只 attach，不 onCreate），再 `installContentProviders()`，最后才 `callApplicationOnCreate()`。系统要保证其他组件在 Application.onCreate 之前就能访问 Provider；代价是 Provider 的 onCreate 全部堵在主线程，是启动优化重点。

**Q5：App Startup 能减少启动时间吗？**

能减少“Provider 数量多、顺序乱、重复初始化”带来的开销，但它仍然是一个 ContentProvider，仍在主线程、仍在 Application.onCreate 之前。它适合做初始化的收敛和依赖排序；如果 `create()` 里做重活，启动不会变快，必须配合懒加载和异步。

**Q6：Baseline Profile 的原理是什么？**

它把冷启动/关键路径上的热点方法写成 profile，安装后由 `ProfileInstaller` 交给 ART 做 AOT 编译，让这些方法以更优模式执行，减少 JIT/解释开销。它不改变进程创建链路，也不替代 App Startup；一个优化“代码跑得快”，一个优化“少跑不必要的代码”。

**Q7：`adj`、`oom_score_adj`、`lmkd`、freezer 是什么关系？**

`OomAdjuster` 算 adj，`ProcessList` 映射成内核 `oom_score_adj`；内存压力下 `lmkd` 按压力和 score 杀进程；freezer 则是先把缓存进程冻结、停止调度，能不杀就不杀。三者是“算优先级—按优先级杀—先冻结保活”的关系。

**Q8：fork 之后为什么先起 Binder 线程池，再进 Looper？**

因为应用进程一启动就可能被 system_server 通过 Binder 调用（attachApplication、bindApplication、生命周期回调），没有 Binder 线程池就无法接收这些请求；而主线程的 Looper 要等 `ActivityThread.main()` 里才准备。顺序是 `nativeZygoteInit()`（Binder 池）→ `applicationInit()` → `ActivityThread.main()`（prepareMainLooper + loop）。
