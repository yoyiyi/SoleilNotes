## 1 PackageManager 与 PackageManagerService

`PackageManager` 是客户端抽象类，`Context.getPackageManager()` 返回的通常是 `ApplicationPackageManager`；它通过 `IPackageManager` 的 Binder 代理调用 system_server 中的 `PackageManagerService`（PMS）。

| 角色 | 位置 | 职责 |
| --- | --- | --- |
| `PackageManager` | `android.content.pm` | 对外 API 抽象类 |
| `ApplicationPackageManager` | `android.app` | 客户端实现，转发 Binder |
| `IPackageManager` | AIDL | 跨进程接口 |
| `PackageManagerService` | `com.android.server.pm` | 扫描、解析、安装、权限、查询 |

```java
PackageInfo info = context.getPackageManager().getPackageInfo("com.example.app", 0);
```

旧版 PMS 直接继承 `IPackageManager.Stub`；较新 AOSP 把 Binder 入口拆到独立的 Impl 类，PMS 本身不再直接继承 Stub，具体以对应版本源码为准。Android 10+ 的查询逻辑大量抽到 `ComputerEngine`/快照，PMS 更像门面。

## 2 PMS 的启动

### 2.1 SystemServer 中的启动时机

`SystemServer.startBootstrapServices()` 启动 AMS 等引导服务后，在 `StartPackageManagerService` 阶段调用：

```java
// 简化示意，参数随版本变化
mPackageManagerService = PackageManagerService.main(
        mSystemContext, installer, domainVerificationService, factoryTest);
```

`main()` 返回后，PMS 由启动代码以 `"package"` 名称注册到 `ServiceManager`。它是 bootstrap 阶段的关键服务，AMS 的组件解析、权限校验等都依赖它。

### 2.2 main() 与构造流程

`main()` 先做编译映射自检，创建 `PackageManagerBg` 后台线程和 `PackageManagerServiceInjector`，再构造 PMS。构造主线：

| 阶段 | 动作 |
| --- | --- |
| 初始化 | `Settings`、`Installer`、`SystemConfig`、`PermissionManagerService` 等依赖 |
| 读状态 | 读取 `/data/system/packages.xml`，恢复包、签名、UID、权限 |
| 扫描 | 扫描 `/system`、`/system_ext`、`/vendor`、`/product`、`/odm`、`/data/app` |
| 收尾 | 处理升级与 dexopt，`systemReady()` 后发送开机广播 |

首次开机或 `packages.xml` 缺失时全量扫描；`mOnlyCore` 为 true 时只扫描核心应用（直接启动等场景）。具体策略以 AOSP 为准。

## 3 APK 解析与 AXML

### 3.1 PackageParser

`PackageParser` 把 APK 中的 `AndroidManifest.xml` 解析成内存模型（包名、版本、`ApplicationInfo`、四大组件、权限、`uses-sdk`、签名等）。入口大致为：

```java
PackageParser.Package pkg = PackageParser.parsePackage(apkFile, flags);
```

解析结果会转为 `PackageSetting`（持久化状态）和 `AndroidPackage`（运行时模型）。Android 12 起解析逻辑逐步迁到 `ParsingPackageUtils`/`ApkLiteParseUtils`/`PackageParser2`，旧类可能保留为兼容层；版本差异以 AOSP 为准。

- split APK 通过 `splitName`、`configForSplit`、`isFeatureSplit` 与 base 关联，由 `parseClusterPackage` 或等价逻辑合并。

### 3.2 AndroidManifest.xml 的二进制格式（AXML）

APK 中的 `AndroidManifest.xml` 被 aapt/aapt2 编译成二进制 XML（AXML），由一系列 chunk 组成：

| Chunk | 类型值 | 作用 |
| --- | --- | --- |
| XML header | `0x0003` | 文件头 |
| String pool | `0x0001` | 标签/属性字符串 |
| Resource map | `0x0180` | 属性名到资源 ID |
| Start/End element | `0x0102`/`0x0103` | 标签与属性 |

属性值是带类型的 `Res_value`（`TYPE_STRING=0x03`、`TYPE_INT_DEC=0x10`、`TYPE_INT_BOOLEAN=0x12`、`TYPE_REFERENCE=0x01`）；文件常以 `03 00 08 00` 开头。

```bash
aapt2 dump xmltree app.apk --file AndroidManifest.xml
apkanalyzer manifest print app.apk
apktool d app.apk -o out
```

PMS 通过 `AssetManager` + `XmlResourceParser`（底层 `ResXMLTree`）读取，而不是普通 XML 解析器。

## 4 签名校验

### 4.1 v1 / v2 / v3 / v4

| 方案 | 引入 | 保护范围 | 关键点 |
| --- | --- | --- | --- |
| v1（JAR） | 早期 | 每个 entry 的摘要 | `META-INF` 下 `MANIFEST.MF`/`.SF`/`.RSA`/`.DSA`/`.EC`；不保护 ZIP 元数据，有 Janus 风险 |
| v2 | Android 7.0 (API 24) | 整个 APK | 签名块位于中央目录前；校验快、防 ZIP 结构篡改 |
| v3 | Android 9 (API 28) | 整包 + 密钥轮换 | 支持签名证书轮换（lineage） |
| v4 | Android 11 (API 30) | 整包 + 增量安装 | 签名在独立 `.idsig`，配合 `fs-verity` 做增量安装 |

v1 只对条目做摘要，攻击者可在不破坏 v1 的情况下改写 ZIP 结构（Janus，CVE-2017-13156，影响部分 Android 5.0–8.0 设备）；v2 对整包签名可挡住。Android 11 起 targetSdk ≥ 30 的 APK 至少需要 v2，仅 v1 会被拒绝安装。

### 4.2 apksigner 实践

```bash
# v2+ 必须先对齐再签名
zipalign -p -f 4 app-unsigned.apk app-aligned.apk

apksigner sign --ks release.jks --ks-key-alias key0 \
  --out app-signed.apk app-aligned.apk
apksigner verify --verbose --print-certs app-signed.apk
```

`jarsigner` 只能产生 v1；`apksigner` 支持 v1~v4。v4 会额外生成 `.idsig` 旁路文件，用于 `adb install --incremental` 等场景。

### 4.3 PMS 中的校验

PMS 在解析阶段通过 `ApkSignatureVerifier`（旧版本为 `PackageParser.collectCertificates()`）依次尝试 v3/v2/v1，得到 `SigningDetails`（证书、方案版本、lineage）。安装/升级时 `PackageManagerServiceUtils.verifySignatures()` 比较新旧签名，不一致返回 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，签名最终写入 `packages.xml` 的 `<sigs>`。

## 5 安装流程

### 5.1 从 PackageInstaller 到 Session

| 步骤 | 参与类 | 说明 |
| --- | --- | --- |
| 建会话 | `PackageInstaller.createSession()` → `PackageInstallerService` | 分配 sessionId |
| 写 APK | `Session.openWrite()` | 写入 stage 目录，常见 `/data/app/vmdl<sessionId>.tmp` |
| 提交 | `Session.commit(PendingIntent)` | 异步交给 PMS，结果走 PendingIntent |
| 安装 | `PackageInstallerSession` → `PMS.installStage()` | 解析、校验、扫描、落盘 |

```java
PackageInstaller installer = context.getPackageManager().getPackageInstaller();
PackageInstaller.SessionParams params =
        new PackageInstaller.SessionParams(PackageInstaller.SessionParams.MODE_FULL_INSTALL);
int id = installer.createSession(params);
try (PackageInstaller.Session session = installer.openSession(id)) {
    try (OutputStream out = session.openWrite("base.apk", 0, -1)) {
        // 把 APK 写入 out
    }
    session.commit(pendingIntent); // PendingIntent.getBroadcast(...)
}
```

`PackageInstallerSession` 把提交事件发给 PMS 的 `PackageHandler`，进入 `installStage()` → `installPackagesTracedLI()`/`installPackagesLI()`。Android 10+ 分为 prepare（解析/签名/ABI）、scan、reconcile、commit 等阶段，方法名随版本变化。

### 5.2 installd 与落盘

PMS 通过 `Installer`（`IInstaller` AIDL）调用 native 守护进程 `installd`：

- `createAppData`：创建 `/data/user/<userId>/<package>`（CE/DE），维护 `/data/data/<package>` 链接。
- `install`/`moveFiles`：把 stage 目录移到最终 `/data/app/...`。
- `dexopt`：调用 `dex2oat` 生成 oat/vdex，配合 `PackageDexOptimizer`、`BackgroundDexOptService`。
- `rmPackageDir`/`destroyAppData`：卸载时清理代码与数据。

完成后 PMS 更新 `packages.xml`，发送 `ACTION_PACKAGE_ADDED`/`ACTION_PACKAGE_REPLACED` 等广播，并通知 `LauncherAppsService` 等观察者。

## 6 PMS 的数据结构

### 6.1 Settings

`Settings` 是 PMS 的持久化状态中心：

| 字段 | 内容 |
| --- | --- |
| `mPackages` | `包名 → PackageSetting`（安装状态、签名、UID、版本） |
| `mSharedUsers` | `sharedUserId → SharedUserSetting` |
| `mUsers` | 用户列表与各用户安装状态 |
| `mPermissions` | 权限定义与授予状态（部分归权限服务） |

`PackageSetting` 持有 `PackageUserState`（每个用户是否安装、stopped、hidden 等）；PMS 内存中另有 `包名 → AndroidPackage` 的运行时模型。

### 6.2 packages.xml

`/data/system/packages.xml` 是包管理数据库，重启后据此恢复。简化结构：

```xml
<packages>
  <version sdkVersion="34" databaseVersion="3" fingerprint="..." />
  <package name="com.example.app" codePath="/data/app/.../base.apk"
           primaryCpuAbi="arm64-v8a" version="1" userId="10123">
    <sigs count="1"><cert key="..." /></sigs>
    <perms><item name="android.permission.INTERNET" granted="true" flags="0" /></perms>
  </package>
</packages>
```

| 文件 | 作用 |
| --- | --- |
| `packages.xml` | 包、签名、UID、权限等主状态 |
| `packages.list` | 包名、UID、数据目录等，供 native/其他服务读取 |
| `packages-stopped.xml` | stopped 状态 |
| `runtime-permissions.xml` | 运行时权限授予状态 |

写入由 `Settings.writeLPr()` 等完成，通常先写备份再替换；不要手工删除或修改。

## 7 权限授予与 PermissionManagerService

- 权限定义由 `SystemConfig` 解析 `/system/etc/permissions/*.xml`、`/vendor/etc/permissions`、`/product/etc/permissions` 等目录得到。
- `PermissionManagerService` 负责权限注册、运行时权限授予/撤销、flags 与 UID 校验；PMS 构造时创建它（新版通过 injector）。
- 运行时权限状态由 `RuntimePermissionsPersistence` 写入 `/data/system/runtime-permissions.xml`。
- 应用侧调用 `checkSelfPermission()`/`requestPermissions()`，服务端最终走 `PermissionManagerService.checkPermission()`；`AppOpsManager` 是另一套 app op 控制。
- Android 11+ 的权限 UI 与默认授予策略主要由 mainline 的 `PermissionController` 承担。

```bash
adb shell pm grant com.example.app android.permission.CAMERA
adb shell dumpsys package com.example.app | grep -A5 "runtime permissions"
```

## 8 应用信息查询 API

### 8.1 getPackageInfo / queryIntentActivities

```java
PackageManager pm = context.getPackageManager();
PackageInfo info = pm.getPackageInfo("com.example.app",
        PackageManager.GET_ACTIVITIES | PackageManager.GET_SIGNING_CERTIFICATES);

Intent intent = new Intent(Intent.ACTION_VIEW, Uri.parse("https://example.com"));
List<ResolveInfo> list = pm.queryIntentActivities(intent, PackageManager.MATCH_DEFAULT_ONLY);
ResolveInfo best = pm.resolveActivity(intent, 0);
```

| Flag | 作用 |
| --- | --- |
| `GET_ACTIVITIES` / `GET_SERVICES` / `GET_RECEIVERS` / `GET_PROVIDERS` | 附带组件 |
| `GET_META_DATA` | 附带 `<meta-data>` |
| `GET_SIGNING_CERTIFICATES` | 附带签名（API 28+，替代 `GET_SIGNATURES`） |
| `MATCH_UNINSTALLED_PACKAGES` | 包含已卸载但保留数据的包 |
| `MATCH_DEFAULT_ONLY` | 只匹配声明了 `CATEGORY_DEFAULT` 的组件 |
| `MATCH_ALL` | 放宽组件过滤；不能用来绕过 Android 11 包可见性 |

Android 13（API 33）起，int flags 重载多被标为 deprecated，改用类型安全的 `PackageInfoFlags.of(...)`、`ResolveInfoFlags.of(...)`、`ApplicationInfoFlags.of(...)`、`ComponentInfoFlags.of(...)`。

### 8.2 Android 11 包可见性 `<queries>`

targetSdk ≥ 30 时，默认只能看到自己、系统应用、有交互的包，以及 `<queries>` 声明过的包；否则 `getPackageInfo()` 可能抛 `NameNotFoundException`，`queryIntentActivities()` 返回空列表。

```xml
<manifest ...>
    <queries>
        <package android:name="com.example.pay" />
        <intent>
            <action android:name="android.intent.action.SEND" />
            <data android:mimeType="image/*" />
        </intent>
        <provider android:authorities="com.example.provider" />
    </queries>
</manifest>
```

`<queries>` 必须是 `<manifest>` 的直接子元素。查询全部应用需要 `QUERY_ALL_PACKAGES` 权限，但 Google Play 对该权限有严格政策限制，优先按包名/Intent 精确声明。

## 9 面试问答

**Q1 PackageManager 和 PackageManagerService 的关系？** `PackageManager` 是客户端 API，`ApplicationPackageManager` 经 `IPackageManager` Binder 调到 system_server 的 PMS；PMS 才是真正的实现。

**Q2 PMS 何时启动？`main()` 做什么？** 在 `SystemServer.startBootstrapServices()` 的 `StartPackageManagerService` 阶段、AMS 之后启动；`main()` 创建后台线程与 PMS，构造时读 `packages.xml`、扫描系统/数据分区、初始化权限与用户服务，随后由启动代码注册 `"package"` Binder。

**Q3 APK 解析解析什么？AXML 是什么？** 解析 `AndroidManifest.xml` 得到包名、版本、组件、权限、签名；AXML 是 aapt2 编译的二进制 XML，由字符串池、资源映射、起止元素等 chunk 组成，PMS 用 `XmlResourceParser`/`ResXMLTree` 读取。

**Q4 v1 与 v2 的区别？为什么 v2+ 要先 zipalign？** v1 按 entry 做 JAR 签名，不保护 ZIP 元数据；v2 对整包签名，能防 Janus 类篡改且更快。v2 覆盖整个文件（含对齐填充），先签名再对齐会破坏签名。

**Q5 从点击 APK 到安装完成经历什么？** `PackageInstaller` 建 session → 写入 stage → `commit` → `PackageInstallerSession` 交给 PMS → 解析/签名/扫描/冲突检查 → `Installer` 调 `installd` 建数据目录并 dexopt → 更新 `packages.xml`、发广播。

**Q6 `packages.xml` 能删吗？** 它是 PMS 的持久化包状态（路径、签名、UID、权限、用户状态）；删除后开机会全量重扫，可能导致权限、stopped 状态丢失，不能手工删改。

**Q7 Android 11 查询不到已安装应用怎么排查？** 检查 targetSdk 是否 ≥ 30、是否受包可见性限制；确认 `<queries>` 是否声明包名/Intent/Provider，或是否持有 `QUERY_ALL_PACKAGES`；再排除组件禁用、用户未安装和 flags 问题。

**Q8 运行时权限授予经过哪些服务？** 请求进入 system_server，由 `PermissionManagerService` 校验并更新状态（持久化到 `runtime-permissions.xml`），UI 由 `PermissionController` 承担，`AppOpsManager` 管独立的 app op。
